# 协议匹配与解码性能改进规划

2026-09-07 · 用户讨论结论、待验证方案与首轮执行结果

本页记录分层分发、连接级解析器缓存、流亲和，以及解码路径的后续改进方向。现有性能结论、环境与原始记录见 [性能评估](PERFORMANCE_ASSESSMENT.md)。初次讨论仅补充文档；用户随后授权先优化链路、再复用 Yak 引擎，首轮已完成的窄范围改动及实测见第 7 节。其余方案仍未实施，不把规划写成已交付能力。

## 1. 范围与基本判断

- 继续遵守 [ACTIVE_SCOPE.md](ACTIVE_SCOPE.md)：#5022、#5023 已先合并；两代样本独立保留；指定的 10 项外层与 4 项识别延期，不借本规划恢复其实现。
- 匹配成本、解码成本、字段树构建及导出成本分别测量。当前应用基准预先指定 rule、entry 和消息边界，因此匹配优化不能解释该基准已有的全部耗时。
- 当前数据支持继续优化通用运行时与对象表示；尚不足以把性能问题归因于 Yak 指令执行本身，或承诺全面改成 Go 后的收益。
- 不新增依赖。保留 YAML / Yak 的扩展与兼容路径；固定数值字段和字节特征优先直接处理，必要的正则按热点再评估。
- 离线解析输入字节率不等于网卡捕获能力、真实持续无损带宽或客户端端到端容量。

## 2. 匹配：分层分发图与连接级快路径

现有 [TCP 规则](rules/transmission_control_protocol.yaml) 已按端口缩小候选范围，随后逐个 `TryProcessByType` 并在失败时回滚，并非每包遍历全部协议。下一步应减少热路径上的动态分支、整套试解析及重复识别。

1. 按链路类型、EtherType、IP 协议号直接查表；将静态规则关系预处理成不可变分发表。树用于展示层级，执行结构允许嵌套、重复封装及协议升级，使用分发图和状态机。
2. 分离 `Probe`、消息边界处理、`Decode` 和导出。Probe 只检查必要字节，至少区分匹配、不匹配和数据不足；限制候选数、探测字节量及未知流预算。
3. 端口、端点历史和可见握手信息用于排序候选，不作为协议确证。TCP 按需重组；分片、截断、中途开始的捕获不能因为首包数据不足就永久判错。
4. 确认后按流保存解析器句柄、版本和会话阶段，后续消息直接进入相应解析器，继续验证帧格式。升级、关闭、超时及端口复用需要转换或失效处理；未知内容保留原始字节和明确状态。
5. 不将加密外层识别解释为已解密的内部应用语义，不以快路径降低原有字段、边界及拒绝合同。

Wireshark 已支持将解析器绑定到 conversation；这里是采用适合本库的机制，不宣称独有能力。[Wireshark conversation API](https://www.wireshark.org/docs/wsar_html/conversation_8h.html)

## 3. 亲和：双向流与 worker 本地状态

建议流键为传输协议、规范化的两个 IP:端口端点，以及必要的捕获接口、VLAN / 隧道作用域。两个端点交换后归属相同，同时保留原始方向；IP 分片在端口不可用时需要相应重组上下文，不能用缺失端口拼出错误连接。

- 同一双向流交给同一个长期 worker，局部持有重组、消息关联、解析器和会话状态。减少共享状态的锁与跨 worker 搬移，维持该流的有序处理。
- 仅按 IP 分配会混合多连接、多协议，并造成热点。端点级协议历史只能作为提示，不能替代精确流键。
- 当前 [TrafficPool](../pcapx/pcaputil/trafficpool.go) 已有双向缓存，但键生成包含地址字符串化、排序、拼接和 SHA-256。候选方案是固定结构体键配合低开销分片哈希，完整键比较仍用于区分碰撞；该路径的实际占比尚未测量。
- worker 逻辑亲和不等于 Go goroutine 绑核，也不等于已经配置硬件 RSS。先测逻辑分片，再评估平台能力，不为此引入额外框架。
- 必须限制流数量、重组内存和空闲时长，处理重置、连接复用和缓存淘汰。单条大流可能成为单 worker 瓶颈；不能通过把同一有状态流的包轮询分发来换取表面均衡。

Linux 的 RSS / RFS 提供按流分发与缓存局部性的参考，但其平台能力不代表本库已实现相同机制。[Linux 网络扩展文档](https://docs.kernel.org/networking/scaling.html)

## 4. 解码归因：已确认的实现与数据

### 4.1 两协议的字节解码已经包含 Go 原生实现

当前 Memcached 和 Cassandra 样本入口通过 YAML operator 调用 Go 函数 [decodeMemcachedFields](parser/stream_parser/memcached_fields.go) 和 [decodeCassandraFields](parser/stream_parser/cassandra_fields.go)。后者已经直接从字节范围读取整数、长度和内容；前者使用字节比较、定位与二进制整数读取。因此，不能把当前完整路径简单视为“由 Yak 逐字节解释整个协议”。

这些函数返回字段描述与元数据后，仍经过 [parseExactByteFieldTreeWithEndian](parser/stream_parser/tls_certificate_tree.go) 创建通用 Node、Cfg、父子关系和字节范围，再初始化节点。完整 JSON 路径还执行 NodeToMap 与序列化。这些阶段不能在归因中合并成纯字节解码。

### 4.2 本轮优化前的准备成本

- [ParseRule](parser/base/base.go) 缓存解码后的 YAML 文档，每次仍深拷贝可变文档并创建独立树；已有缓存不等于已有可直接执行的不可变解析计划。
- [ExecOperator](parser/stream_parser/vm.go) 每次构造绑定当前节点的回调集合、YakNode 和新引擎，然后导入绑定并执行。
- [operator_program.go](parser/stream_parser/operator_program.go) 已缓存序列化程序，避免符合条件的脚本反复编译，但每次仍反序列化指令与符号表以隔离可变状态。不能把“增加编译缓存”当成尚未完成的新方案，也不能直接共享当前可变 VM 或指令对象。
- [Config.SetItem](parser/base/node.go) 除写入值，还记录赋值闭包供后续重放。现有小配置存储优化保留了该语义；不能未经兼容分析直接删除历史、共享可变树或去掉所有锁。
- 基础标量 `out` 已有原生快路径，其余表达式仍走动态求值；后续应补足适用的结构化操作，不能宣称从零引入这种机制。

### 4.3 已测分配说明对象成本值得优先处理

下表由 [第四轮原始日志](reports/config-store-20260907/application-benchmarks.txt) 的新后端单 worker 三次结果分别取中位数，再除以每轮 11 条消息。相同 1,421 B 输入，平均每条约 129 B；混合样本包含 48 项统计响应，不表示每条消息大小或成本相同。

环境为 M1 Max、10 CPU、64 GiB、macOS 14.1.2、Go 1.22.12，非独占桌面；预热与样本加载不计时。程序身份、运行顺序、最小–最大范围及全部原始值见 [第四轮报告](reports/config-store-20260907/README.md)，本次未重新测量。

| 路径 | 平均摊销耗时 ↓ | 累积分配 / 消息 ↓ | 分配次数 / 消息 ↓ |
| --- | ---: | ---: | ---: |
| 指定入口、完整字段树 | 193.7 μs | 147.1 kB | 2,441 |
| 同上，加完整投影与 JSON | 237.7 μs | 167.3 kB | 2,924 |

耗时是整批基准的每消息摊销，不是单条延迟分位数。分配是累计分配量，不是常驻内存需求或泄漏证据；不能用两个中位数之差精确分摊 GC、VM 或 JSON 的独占成本。基准每轮新建 goroutine / channel，后续还应独立测长期 worker 的稳态路径。

相同工作量下，第四轮小配置存储让单 worker 应用字段每轮中位耗时从 2.776 ms 降到 2.130 ms，吞吐提高约 30.3%，完整 JSON 从 3.319 ms 降到 2.615 ms，吞吐提高约 26.9%；它没有更换 Yak VM 或删减输出。数据支持优化对象表示的方向，不提供剩余成本的精确占比。

历史 [alloc_space](reports/performance-20260906/alloc-top.txt) 中 ExecOperator 的累计分配还包含其调用的 Go 解码器与建树过程；不能把该累计占比当作 Yak 指令执行的 CPU 占比。旧 CPU profile 对路径检查的高占比也未产生同量级干预收益，预加载原型已撤回，见 [反证实验](reports/performance-20260906/OPTIMIZATION_EXPERIMENTS.md)。下一轮应重新采集对应版本的 profile，避免依据旧热点或累计调用栈直接决定重写。

## 5. 解码改进候选与优先顺序

以下顺序是待验证建议，不是已实现状态或保证收益。

1. **先拆分成本。** 在固定样本上分别测原生字段解码、接通用字段树、公开 ParseBinary、完整 JSON；原生入口和完整入口工作量不同，仅用于分解成本，不能直接拿二者作等价加速比。另设相同字段、元数据与输出合同的原生直接入口 / Yak 包装对照，量化绕过包装的净收益。
2. **不可变解析计划与每消息状态分离。** 从规则预处理字段类型、长度、字节序、子节点和入口索引，运行时只分配游标、动态值和事务状态。保留 YAML 编辑入口；公开可变 Origin / Cfg 需兼容层或写时复制，不能共享旧的可变节点树。此方案不同于已撤回的路径预加载实验。
3. **结构化原生算子入口。** 对已经是 Go 解码器的固定 profile，评估通过显式注册句柄直接调用，保留同样的边界、错误和事务行为；自定义 operator 保留 Yak。不要通过不可靠的脚本文本替换猜测语义，生成路径和未知规则必须有明确回退。
4. **紧凑字段表示，降低建树放大。** 评估 FieldID、类型、字节 / 位范围与连续字段数组；静态描述共享，父子关系可用索引。字段数已知时合理预分配。先保留完整信息并提供 Node 适配层，再单独评估摘要模式，不能靠删字段报告完整模式加速。
5. **减少重复字节及值表示。** 原始消息保持有明确所有权和生命周期的只读缓冲区，内部字段先引用范围，按需生成字符串、字节副本及导出对象。不得把可复用抓包缓冲区直接暴露给长生命周期结果；公开结果的独立性、空值形状与精确数值类型必须保留。
6. **按实测决定进一步 VM 优化。** 若剩余 CPU 明确集中在引擎建立、指令加载、绑定或动态调用，再评估不可变代码与可变 frame 分离、按需绑定和受控状态复用；保留动态 eval、闭包隔离、源码定位与 panic 恢复。不要先对整个 Yak VM 做广泛重写，也不要未经生命周期证明就池化结果树。
7. **导出与消费解耦。** 全量解码 / 完整导出继续作为独立模式；客户端与 aid 可先查询流摘要、再按需展开字段与字节证据。不同输出模式独立报告性能，原始数据、完整校验及来源定位不因摘要模式丢失。

## 6. 下一轮实验与验收合同

> 首轮配置写入 / 裸类型建树与受限 Yak 桥接复用已完成消融对照，见第 7 节。其他候选、长期流 worker 和真实容量仍待验证；不把本轮局部收益解释为整个 Yak 包装成本。

- 先选已有样本：两代 Memcached 二进制 GET、48 项文本统计响应、Cassandra 初始消息，再加现有长列表、非字节对齐字段、动态 operator 和负样本。实现后扩展到受影响的全部存量与新增样本，不能只保留容易的消息。
- 分别测指定入口、新连接识别、已确认连接和端到端处理；记录 probes / flow、失败回滚次数、ns / message、B / message、allocs / message、吞吐、队列丢弃与 P99。新连接创建率与单条大流单独测试。
- 冷启动和预热稳态分开；使用长期 worker 并保留旧基准供对照。至少三次独立重复，顺序交替，保留慢值、错误、超时、构建身份和 manifest 摘要，不在性能计时期间并行编译或跑回归。
- CPU、分配、阻塞 / 锁等采样分开执行，避免互相干扰；不能把累计调用栈重复相加，也不能把采样百分比直接当作可消除耗时。[Go 诊断文档](https://go.dev/doc/diagnostics)
- 等价性包含字段名、顺序、重复项、数值类型、空值、元数据、原始范围、最终读取位置、拒绝合同、事务回滚、不同输入隔离与并发行为；结构化生成和自定义规则保持兼容。
- 本次文档更新不跑全量。实现时先定向验证；公共后端冻结后根据影响面安排一次完整回归，并单独报告已有失败，不能用局部性能或摘要等价替代语义正确性。
- 真实捕获、重组、输出、客户端和 AI 调用仍需独立端到端测试；新增离线吞吐不得直接升级成实时带宽或模型能力承诺。

## 7. 已执行：先链路、再 Yak 复用

用户授权后，先将配置写入与历史追加合并为单次加锁，为裸字段类型减少字符串切分；随后为闭合桥接语法增加独占引擎池，复用库绑定和已装载程序。每次作用域独立，结束后清空报文引用；嵌套调用另借引擎。128 个 operator / 42 个原生绑定可使用该路径，动态 eval、include、闭包和其他自定义程序保留独立运行时。没有增加依赖或修改 Yak VM 核心，也没有实现分层匹配、流亲和或延期协议。

相同 11 条消息、1,421 B 输入，三个冻结版本各 3 次、2 s 窗口：单 worker 字段吞吐合计提高 17.4%，完整 JSON 提高 14.4%；后者链路阶段提高 7.4%，Yak 阶段再提高 6.5%。10 worker 完整 JSON 合计提高 11.5%，到约 9,284 消息/s、9.59 Mbps 应用输入字节率，不代表网卡捕获或无损带宽。短窗口波动与慢值、全部分阶段数据和采样限制均保留在 [本轮报告](reports/path-worker-20260907/README.md)。

全部 58,533 条封装记录和 11 条应用消息的完整输出摘要在三个版本间一致；受影响协议族、parser 三包回归及选定 race 检查通过。本轮未运行整个库或仓库全量。当前分配热点仍集中在配置历史与建树；下一步评估其表示方式，不将累计调用栈当成纯 Yak 指令成本。

## 8. 已执行：配置历史数据化与批量构树

普通赋值历史改为私有有序键值记录，仅在公开读取函数列表或复制全部配置时按原接口物化闭包；自定义回调、公开切片修改、重放顺序和浅共享继续兼容。表达式恢复只查询历史状态，不再为计数触发物化。新配置在私有状态中批量初始化，共享字节字段树预分配子节点并一次组装字段配置，保留完整输出和失败回滚。

第一版精确容量导致后续初始化再次扩容，分配量反而高于仅历史优化版。最终采用带余量的容量分档，重新冻结并完整对照；失败假说、慢值、原始数据和复现脚本均保留在 [配置与建树报告](reports/config-tree-20260907/README.md)。

相对于已包含第 7 节优化的本轮基线，相同 11 条消息 / 1,421 B、2 s 窗口、每组 3 次：单 worker 完整字段吞吐提高 44.7%，完整 JSON 提高 32.5%；10 worker 分别提高 44.7% 和 29.7%。单 worker JSON 累计分配由 1,665,860 降至 1,398,166 B/批，分配次数由 28,938 降至 14,387。10 worker 完整 JSON 约 11,935 消息/s、12.33 Mbps 应用输入，仍不是实时网卡无损容量。

后续重点仍是不可变解析计划、配置与字段表示进一步压缩、完整导出减少中间对象。长期 worker、分层识别和双向流亲和独立评估；本轮没有扩展 Yak 复用语法、延期协议、客户端或 aid 集成。

最终版 605 个选定顶层样本测试全部通过、无跳过；全部 58,533 条封装记录与 11 条应用消息的导出摘要在四个冻结版本间一致；parser 三包回归和选定 race 检查通过。此验证覆盖旧 / 新样本的现有合同，不等于整个库全量或所有协议语义完成。

## 8. 本轮完整路径与 P0 验收（2026-09-07）

相对 `5b6cbe1f8` 的完整 JSON 倍速优化已完成正式验收，最终程序固定到 `35607643c`。采用紧凑配置编号与共享不可变默认值、按字段数量准备独立节点、静态规则构树计划、直接结果窗口读取、完整投影预分配，以及十个固定 Memcached/Cassandra 桥接程序的原生调用。失败结果仍通过原 Yak 程序生成原有错误，读取事务与回调只执行一次。复杂 operator、动态 out、导入和生成继续使用兼容路径。AllJoyn 大计数负载曾出现持续回退，最终通过一次实时读取结果范围及 consumed bits 减少重复锁与查询，保留动态修改及事务语义。

P0 增加 LDAP Bind 响应、Unbind、Search 消息和完整 SMB3 Transform 边界入口。四项以显式消息合同验收，能力目录继续为 `partial`，评分保持实际证据对应的 B 级。见 [范围与证据](P0_SCOPE.md)。单 worker 完整 JSON 吞吐达到 2.008859 倍，10 worker 达到 1.892561 倍；40 个代表负载组合均没有超过 5% 的回退。全包回归及相关 race 已通过；正式指标、各阶段源代码/程序摘要、所有慢值与撤回实验统一保存在 [本轮报告](reports/hotpath-20260907/README.md)。

后续优先事项：先扩展有独立正确性证据的代表负载，再依新 profile 决定是否继续压缩导出和构树成本。不得直接把累计调用栈视为可消除成本。YAML 克隆计划、合并初始化遍历和更小配置索引的试验未保留；其失败或无稳定收益证据在报告中。当前未启动流亲和、TCP 重组、真实捕获容量、客户端或 aid 集成，原有十四项延期维持原范围。
