# 当前性能与使用边界

最终实抓结果来自 2026-09-12 的 Windows amd64 / Intel i5-13490F / Go 1.22.12 /
Npcap 1.88。本次文档和资源懒加载整理不属于新的吞吐成绩。

## 完整抓包分析

独立进程生成本机 HTTP/HTTPS/MQTT socket 流量，24 客户端、4,096 字节 body，
每 128 次操作重新建连。分析器抓 Npcap loopback，完成 TCP 重组、分帧、完整字段
和 metadata，保留 4,096 条 / 32 MiB 原始消息历史；没有逐条 JSON 编码。
TLS 密文只解释既有记录结构，没有解密内部 HTTP。

| 应用输入目标 | worker | 保存 pcap | 持续负载 | 活跃完整解码 Mbps | 进程 CPU 秒 | 驱动丢包 |
|---|---:|---|---:|---:|---:|---:|
| 500 Mbps | 1 | 是 | 20 s | 512.05 | 10.0625 | 0 |
| 1 Gbps | 1 | 否 | 20 s | 1,024.85 | 13.90625 | 0 |
| 2 Gbps | 2 | 否 | 12 s | 2,051.42 | 15.9375 | 0 |
| 2 Gbps | 4 | 否 | 12 s | 2,050.88 | 18.09375 | 0 |

四轮完整解析全部交付消息；未知、上下文缺失、截断、坏包、资源限制、缺口、
回调 panic 和结束残留均为零，生成器收发核验通过。活跃解码是每秒窗口中位数。
输入仅计应用 body；解码含协议头；捕获另含链路/IP/TCP 头。CPU 为进程 user+system，
包含少量开场、收尾和排空。这些数字不是消息延迟 p99。

已知边界：

- 单 worker、2 Gbps、12 秒出现 71,261 个驱动丢包，不计作成功容量。
- 单 worker、1 Gbps、同步保存、30 秒仍会丢包，32/128 MiB 缓冲都不能稳定解决。
- 2 workers 的 2 Gbps 轮已有队列背压，尚未验证小时级稳定性和双机物理网卡线速。
- 任意小包/高建连/数百种复杂协议混合没有容量保证。UDP 解析仍在 reader 上，
  增加 TCP worker 不会自动提升 DNS-heavy 的并行度。
- 当前工具提供消息查看和自动化基础，协议覆盖、TLS 解密与排障 UI 不等同于 Wireshark。

## 离线完整链路

| 内存预载入 pcap、重组、分类和完整字段 | worker | 成功解码 Mbps |
|---|---:|---:|
| 原始 8 份 pcap | 1 / 2 / 4 | 571.28 / 160.96 / 117.76 |
| 频繁 TLS 握手＋DNS/HTTP/MQTT | 1 / 2 / 4 | 646.56 / 1,090.32 / 1,573.84 |

原始样本每批 108 条 / 78,033 成功解码字节 / 81,028 交付字节，两个既有错误文件
保留错误。小批次多 worker 初始化成本不能代表长流扩展性。握手混合每批
5,128 条 / 2,241,920 字节，单 worker 进程 CPU 约 27.78 ms/批。
一份保存的 1 Gbps 流量文件温缓存回放约 2.91 Gbps，不属于实时网卡容量。

字段对象/集合创建、映射写入和 GC 仍是解析热点。亲和避免逐消息重复探测，
但不保证大量同端口启发式规则的首次分类成本。未知、截断、跳过字段和 deferred
输出不得计入完整解码带宽。

## 复现

构建与本地压测命令见 [CLI 指南](../pcapx/cmd/README.md)。只测 1/2/4 worker，
记录完整消息数、成功字节、CPU、捕获丢包、重组缺口与解析错误。

```sh
go test ./common/pcapx/pcaputil -list 'Benchmark.*BinParser'
go test ./common/bin-parser -list 'Benchmark.*Structured'
```

先固定两版程序再交替运行，计时期间不编译或跑回归。报告及原始实验数据放在仓库外。
Windows 原生抓包 pprof 可能混入等待，CPU 总量以进程 user+system 为准；解析热点
使用不含原生等待的回放 profile 定位。
