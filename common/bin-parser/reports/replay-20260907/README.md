# 有限队列持续回放评估

2026-09-07 · 当前 Memcached/Cassandra 捕获 · 本地已知 profile 测量

## 结论

本轮没有得到可以承诺的实时无丢包最大带宽。4 worker、2 Mbps 的三轮 10 秒回放均无丢弃，但延长到三轮 30 秒后，两轮分别丢弃 25、27 条，第三轮无丢弃；丢弃率为 0–0.0369%。因此，短测无丢弃不能升级为长期无损保证。

4 worker、8 Mbps 时，三轮记录丢弃率为 38.48%–39.12%；10 worker 时仍为 24.66%–25.91%。增加并发改善了过载条件下的完成吞吐，却没有消除所有队列溢出。这个结果限定于 **64 条队列、同进程投递调度、当前 38 条记录循环以及完整 JSON 导出**，不是任意队列、任意协议或真实网卡的容量上限。

本轮仅增加测试回放器、统计脚本与报告，没有修改生产解析器、客户端、aid、支持标签或依赖。指定的 14 项仍延期；历史 P0 状态门槛的四项失败也未被本轮结果替代。

## 调度和指标含义

- 每个 worker 处理独立完整记录；同一 worker 内顺序执行封装、应用及 JSON。profile、消息边界、方向和阶段由已知样本给定，不测自动识别、TCP 重组、流状态选择或按流保序。
- 文件与帧顺序保留，原 PCAP 时间间隔被指定的恒定捕获字节率替换。计划到达时刻按累计字节精确计算；字节预算足够时整条记录才到达。
- 输入 Mbps = 捕获记录字节数 × 8 / 计划窗口秒数 / 1,000,000。它包含所选捕获中的协议头，排除 PCAP 容器、链路物理开销及未捕获字节；不能与前两轮的应用字节率直接比较。
- 投递端不等待队列空位，也不等待解析完成。队列满则记录丢弃，不偷偷降低到达速率。投递迟到时沿原时间表赶上，并记录全部投递的迟到量，包括最终被丢弃的记录。
- 处理总延迟从**计划到达时刻**开始，包含投递迟到、排队与服务；排队、服务耗时另行记录。总延迟分位数仅针对已接受的记录，丢弃记录没有虚构完成时间，必须与丢弃率一起读。
- 计划窗口结束后排空已接受记录，单独记录窗口内完成字节率和包含排空时间的完成字节率。成功处理与丢弃的记录数、字节数及每个原始 frame 的计数均守恒；所有正式轮次解析错误为 0。
- 队列长度是并发采样观察值，可能低于真实瞬时高水位；64 条为强制容量。计时含回放计数、观测切片和每条记录测时的开销，未宣称零开销仪器。
- 输入读取/校验、预热和计划生成在计时外；JSON 留在进程内并统计字节，不含写盘、RPC、数据库、模型调用或 UI 渲染。每轮前 GC、每轮后排空并重置；累计 510 秒不能说成一次不间断的长连接运行。

## 为什么不能宣布“最大带宽已经达到某个值”

3 Mbps 长测、10 worker 的三轮都发生少量队列丢弃；2 Mbps 的长测也未能保持三轮无丢弃。这足以否定在本条件下给出无损承诺，但不足以确定解析器单独的服务上限。

同进程投递会受桌面和 Go 调度影响。2 Mbps 长测的投递迟到最大值为 21.33–27.14 ms，全部投递的 P99 仍只有约 0.79–1.08 ms；个别长延迟后集中赶上可能增大队列压力。这里记录的是同时出现的现象，未通过隔离投递、改变队列或 CPU 绑定的对照实验确定唯一原因，不能断言都是 GC、操作系统或解析器造成的。

不能由一次小规模回放外推 100 Mbps / 1 Gbps 深解析，也不能用扩大队列掩盖持续过载。下一步可分别检验投递侧抖动、有限缓冲吸收能力、完整规则树与配置分配；任何优化需同程序、相同样本、无字段裁剪的输出等价和实际计时对照。

## 客户端与 aid 的含义

对于离线 PCAP，使用有界背压可让输入等待处理，避免本轮模拟实时到达采用的队列丢弃；代价是完成时间增长。这是架构建议，尚未实现或测试真实客户端。解析放在后台、允许取消、分页和按需展开字段，仍比在 UI 线程逐包完整构树更符合当前测量边界。

本轮每循环 JSON 为 33,820 字节，约为捕获输入的 8.68 倍；比值不同于前两轮应用消息的 17.81 倍，因为分母和负载不同。输出字节不是 token 数。aid 应消费有界、可追溯的字段证据，而不宜将全部逐包 JSON 直接拼入上下文；本轮没有调用模型，没有新增 AI 正确率、模型时延或客户端帧率结论。已有连接缺口与 12 项样本评估题仍见 [主报告](../../PERFORMANCE_ASSESSMENT.md)。
