## Few-Shot 示例（必须参考）

### 示例1：子任务边界判断（最重要！）
**场景**：父任务是"执行全面主机扫描"，当前子任务 `1-1` 是"获取操作系统类型"
**INPUT**：执行 `uname -s` 返回 `Darwin`

**错误判断**：
```json
{"@action": "verify-satisfaction", "user_satisfied": false, "completed_task_index": "", "reasoning": "任务未完成：仅获取了操作系统类型，还需检查端口、进程、安全配置等"}
```
错误原因：把父任务目标当成了当前子任务的判断标准

**正确判断**：
```json
{"@action": "verify-satisfaction", "user_satisfied": true, "completed_task_index": "1-1", "reasoning": "目标达成：当前子任务要求获取操作系统类型，已成功获取为Darwin"}
```
正确原因：只判断 `<|CURRENT_TASK_...|>` 中"获取操作系统类型"这个目标是否达成

### 示例2：简单子任务的快速完成
**场景**：当前子任务 `1-2` 是"检查磁盘空间"，执行 `df -h` 成功返回磁盘信息

```json
{"@action": "verify-satisfaction", "user_satisfied": true, "completed_task_index": "1-2", "reasoning": "目标达成：成功获取并分析了磁盘空间使用情况"}
```

### 示例3：子任务确实未完成
**场景**：当前子任务 `1-3` 是"分析高CPU进程"，但只执行了 `ps aux` 列出进程，还没分析

```json
{"@action": "verify-satisfaction", "user_satisfied": false, "completed_task_index": "", "reasoning": "任务未完成：仅列出了进程，还需分析哪些进程CPU占用高"}
```

### 示例4：工具执行成功但当前子任务目标未达成
**场景**：当前子任务 `1-4` 是"修复权限问题"，但只是用 `ls -la` 查看了权限

```json
{"@action": "verify-satisfaction", "user_satisfied": false, "completed_task_index": "", "reasoning": "任务未完成：已定位权限问题但尚未修复，需用 chmod 实际修复"}
```

### 示例5：同时完成多个子任务
**场景**：在执行子任务 `2-1` 时，顺带也完成了子任务 `2-2` 的目标

```json
{"@action": "verify-satisfaction", "user_satisfied": true, "completed_task_index": "2-1,2-2", "reasoning": "目标达成：子任务2-1(部署服务)和2-2(验证服务)均已完成"}
```

### 示例6：工具返回结果少但任务已完成（禁止自行发明量化标准！）
**场景**：当前子任务 `1-2` 是"提取目标页面内容观察回显"，使用 URL 内容提取工具访问了 XSS 测试页面，工具返回了页面文本 "Hello admin"（11字），工具日志显示 "content extraction complete, total text: 11 chars"

**错误判断**：
```json
{"@action": "verify-satisfaction", "user_satisfied": false, "completed_task_index": "", "reasoning": "任务未完成：当前子任务要求提取文本摘要，实际内容不足50字，未达标"}
```
错误原因："50字"是你自行发明的标准，任务描述中没有任何字数要求。工具已明确声明提取完成。

**正确判断**：
```json
{"@action": "verify-satisfaction", "user_satisfied": true, "completed_task_index": "1-2", "reasoning": "目标达成：工具已完整提取页面内容，内容少是页面本身特征而非提取失败"}
```
正确原因：工具成功执行且日志确认"提取完成"，内容少是目标页面的真实情况

### 示例7：安全测试中的 HTTP 请求观察
**场景**：当前子任务 `1-3` 是"发送 HTTP 请求并观察响应特征"，使用 HTTP 请求工具发送了请求，响应 200 OK，body 只有短文本

**正确判断**：
```json
{"@action": "verify-satisfaction", "user_satisfied": true, "completed_task_index": "1-3", "reasoning": "目标达成：已成功发送请求并获取到服务器响应特征"}
```

### 示例8：Evidence 只在关键新增发现时填写
**场景**：只是尝试了一个 payload，但没有形成值得后续复用的新结论**

```json
{"@action": "verify-satisfaction", "user_satisfied": false, "completed_task_index": "", "reasoning": "任务未完成：仅完成试错，仍需继续验证", "evidence": []}
```

### 示例9：Evidence 不能只写结论，必须写"主体 + 动作 + 观测 + 控制含义"
**场景**：simple_crawler 已识别出后续值得继续验证的接口与一个明确事实**

**错误写法**：

直接把多行 evidence 塞进 JSON 字符串，或者只写"主体 + 结论"，都不应作为 few-shot 模版。

错误原因：这种写法同时有两个问题。一是 evidence 结构不完整，缺少动作、观测、控制含义。二是模型容易照抄成 JSON 转义长字符串，导致实际输出出现格式畸形。

**正确写法**：

```json
{"@action": "verify-satisfaction", "user_satisfied": false, "completed_task_index": "", "reasoning": "任务未完成：已识别新增测试入口，仍需逐个验证", "evidence": [{"op": "add", "id": "sqli_user_id", "content": "主体: 接口 GET /user/id\n动作: 发送参数 id=1' 的请求并与基线响应对比\n观测: 基线请求返回 200；注入请求返回 500，响应体包含 SQL syntax error near\n控制含义: 该入口应进入 SQL 注入差异复测链路，优先测试闭合与注释变体"}, {"op": "add", "id": "xss_echo_reflect", "content": "主体: 接口 GET /xss/echo\n动作: 发送参数 q=<svg/onload=alert(1)> 的请求并读取响应体\n观测: 响应状态码为 200，响应体原样回显 <svg/onload=alert(1)>\n控制含义: 该入口应进入反射型 XSS 复测链路，优先做浏览器执行验证"}, {"op": "add", "id": "jwt_alg_none", "content": "主体: 接口 POST /jwt/unsafe-login1\n动作: 使用 alg=none 的 JWT 发起登录请求\n观测: 响应状态码为 200，服务端返回带用户信息的登录成功结果\n控制含义: 当前存在可继续利用的不安全 JWT 登录路径，应核验是否可以稳定伪造不同身份"}]}
```

### 示例10：对抗性测试中的黑箱实验与反馈迭代
**场景**：安全测试中目标系统对输入进行过滤。Agent 进行了三次实验：A 和 B 都收到了与基线相同的拒绝响应（15 字节固定文本），但 C 收到了完全不同的响应（60KB 数据）。

```json
{"@action": "verify-satisfaction", "user_satisfied": false, "completed_task_index": "", "reasoning": "任务未完成：实验C的响应偏离拦截基线(信息量最大的观测)，黑箱内部有不同处理路径被触达，主循环应沿C方向负反馈迭代(微调参数逼近目标)，不切换回A/B方向", "evidence": [{"op": "add", "id": "blackbox_model", "content": "主体: 目标黑箱的输入/输出映射模型\n动作: 三次实验分别从不同子空间构造输入\n观测: 实验A→基线拒绝(15B), 实验B→基线拒绝(15B), 实验C→非基线响应(60KB) — C的输入穿过了过滤层到达了下游处理器\n控制含义: C的输入构造方式处于黑箱的接受空间内, 可能性空间已从全集缩小到C附近的子空间, 后续实验应在此子空间内迭代"}, {"op": "add", "id": "interpreter_model", "content": "主体: 黑箱的下游处理器类型\n动作: 审计源码确认输入流经的解释器\n观测: 输入最终由特定类型的解释器处理\n控制含义: 后续payload必须是该解释器的合法语法, 其他解释器的语法在此黑箱内无意义(共轭控制的L变换必须匹配目标域)"}]}
```

### 示例11：任务漂移只触发纠偏，不证明完成
**场景**：父任务是"渗透测试与FLAG获取"，当前子任务 `1-1-1` 是"FTP 后门登录尝试"。Agent 只尝试了一次触发并看到 6200 端口关闭，之后持续测试 `/capture` 端点命令注入（属于子任务 `1-2-1`）。当前 INPUT 显示 agent 执行了 `curl http://target/capture?cmd=;id`。

**错误判断**：
```json
{"@action": "verify-satisfaction", "user_satisfied": true, "completed_task_index": "1-1-1", "reasoning": "Agent 已越界测试 Web 端点，说明 FTP 后门验证已经完成"}
```
错误原因：把执行焦点漂移当成完成证据；一次触发后端口关闭只说明本次未命中，尚不足以排除当前假设。

**正确判断**：
```json
{"@action": "verify-satisfaction", "user_satisfied": false, "completed_task_index": "", "reasoning": "任务未完成：当前动作已漂移到 Web 子任务，且 FTP 假设只有一次触发失败，没有足以区分版本不受影响、触发条件错误或链路受阻的证据；主循环应回到当前 FTP 验证目标并改进实验"}
```
正确原因：漂移只用于纠偏；完成必须由 FTP 子任务自身的证据支持。

### 示例12：单次阴性尝试不等于验证完成
**场景**：当前子任务 `1-1-1` 是"vsftpd 3.0.3 后门漏洞验证"，Agent 使用 bash 执行了后门触发脚本，发送了 `USER user:)` 到 FTP 端口，检查后门端口 6200，返回结果为"Port 6200 is still closed. Backdoor likely not present or patched."

**错误判断**：
```json
{"@action": "verify-satisfaction", "user_satisfied": true, "completed_task_index": "1-1-1", "reasoning": "目标达成：端口 6200 关闭，因此后门漏洞不存在"}
```
错误原因：把一次 payload 未触发直接推广为漏洞不存在；没有验证服务版本、触发前提、请求是否到达目标处理路径，也没有区分“漏洞不存在”和“实验条件错误”。

**正确判断**：
```json
{"@action": "verify-satisfaction", "user_satisfied": false, "completed_task_index": "", "reasoning": "任务未完成：当前仅确认一次触发后 6200 端口仍关闭；需核对版本与触发条件，并设计能够区分漏洞不存在和触发链路错误的对照实验后再形成阴性结论"}
```
正确原因：阴性结果可以完成验证任务，但关闭依据必须具有区分力；这里缺少的不是固定次数，而是能够排除替代解释的实验。

## 典型响应格式

**任务完成时（必须设置 completed_task_index）：**
```json
{"@action": "verify-satisfaction", "user_satisfied": true, "completed_task_index": "任务索引", "reasoning": "简明扼要分析", "evidence": []}
```

**任务未完成时（completed_task_index 为空）：**
```json
{"@action": "verify-satisfaction", "user_satisfied": false, "completed_task_index": "", "reasoning": "简明扼要分析：下一步应用新 payload 复测并对比响应差异", "evidence": [{"op": "add", "id": "health_403", "content": "主体: 接口 GET /health\n动作: 发送未带认证头的健康检查请求\n观测: 响应状态码为 403，响应头包含 x-auth-required: true\n控制含义: 应切换为携带认证头的请求，不再沿无认证分支重复测试"}]}
```

注意：以上示例都没有 `todo_delta` 字段 —— 该字段已从 verification schema 移除。verification 不维护 TODO；主循环只能在后续正常 action 中按需携带可选 `todo_delta`。

### 示例13：宣告完成时仍有残留 TODO 的客观门

**场景**：当前子任务 `1-1` 是"获取操作系统类型"，已经成功获取为 `Darwin`。但当前 task scope 中还有 `verify_kernel_version` 和当前焦点 `collect_uptime` 两个开放 TODO（由主循环正常 action 的 `todo_delta` 维护），而你判断当前子任务的目标已经达成。

**错误判断（系统会强制回退）**：
```json
{"@action": "verify-satisfaction", "user_satisfied": true, "completed_task_index": "1-1", "reasoning": "目标达成：已获取操作系统类型为 Darwin"}
```
错误原因：当前 task scope 仍有开放 TODO，系统会作为客观门把 `user_satisfied` 强制回退为 `false` 并写入 `[VERIFICATION_TODO_INCOMPLETE]` timeline，相当于你这一轮 verification 的 satisfied 判定被推翻。

**正确判断（如实指出残留 TODO，交由主循环关闭）**：
```json
{"@action": "verify-satisfaction", "user_satisfied": false, "completed_task_index": "1-1", "reasoning": "子任务目标已达成(操作系统类型=Darwin)，但当前 task scope 仍有 2 项开放 TODO(verify_kernel_version/collect_uptime)，需主循环继续执行，并在正常 action 中用 todo_delta 留痕关闭后再宣告完成"}
```
正确原因：verification 不负责关闭 TODO，只需在 `reasoning` 中如实指出残留工作；主循环在后续正常 action 中顺手维护 TODO，下一轮 verification 再确认 satisfied。

### 示例14：已确认安全风险但尚未上报/留档（必须先落档）

**场景**：当前子任务是验证登录接口的 SQL 注入。已用真实请求 `username=' OR '1'='1` 拿到与基线不同的响应（认证被绕过），漏洞已被一手数据确认。但此时既没有调用 `cybersecurity-risk` 落库，也没有把证据写入任何 output 结果文件。

**错误判断（系统视同未交付）**：
```json
{"@action": "verify-satisfaction", "user_satisfied": true, "completed_task_index": "1-1", "reasoning": "目标达成：已确认登录接口存在 SQL 注入"}
```
错误原因：漏洞已确认却既未落库也未留档，属于"视同未交付"。确认 != 交付，此时不允许宣告完成。

**正确判断（保持未完成，在 reasoning 中要求落档）**：
```json
{"@action": "verify-satisfaction", "user_satisfied": false, "completed_task_index": "", "reasoning": "风险已确认但未落档：登录接口 SQL 注入需主循环先经 cybersecurity-risk 上报或写入结果文件留档后再宣告完成", "evidence": [{"op": "add", "id": "sqli_login_confirmed", "content": "主体: 接口 POST /login\n动作: 发送 username=' OR '1'='1 的登录请求\n观测: 响应状态码为 200，返回带管理员身份的会话，与基线拒绝响应形成差异\n控制含义: 认证绕过已被一手数据确认，必须落档为持久化交付物"}]}
```
正确原因：把"上报/留档"作为必须完成的交付动作在 `reasoning` 中点明，主循环 AI 会据此调用 `cybersecurity-risk`，并可在同一正常 action 中携带 `todo_delta` 更新工作集；落档完成后才可在后续轮宣告该子任务完成。每个独立风险实例都单独上报，不攒到末尾批量补录。
