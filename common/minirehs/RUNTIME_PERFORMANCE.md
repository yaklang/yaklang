## T01 当前 Windows 基线（v5 / eb74d7d0b）

实际 GetRequest 为 4941 条；MITM 为原始 89 条中可编译的 87 条，33/43 的编译失败单列记录。
真实语料为完整 1332 条、5,247,590 输入字节；一轮语料耗时不等于一条请求的延迟。
短扫描的 1x 计时有缺失，保留为 unavailable，另以五轮 200 ms 测得编译后/镜像加载后预热扫描
约 131.1/139.2 µs。生产权重、排队延迟、原生 PMU 和实际冷盘 I/O 未测。

磁盘镜像 **1,454,565 B**，但 raw C blob 为 **30,165,009 B**，C 表实际请求 **32,919,577 B / 44,490 次分配**。
这三者不能混用。C close 后请求内存及存活分配均归零；没有将该组件计数当作整个进程 RSS。
其中 dense follow 为 17,386,928 B，2,173,366 个 word 中 1,557,804 个为零，约 **71.7%**。
因此文件压缩已有效，运行表、重复恢复和布局仍有空间。现有 GetRequest 的空 conditional-follow
表只有一张、25,600 B；单修此表不能宣称解决了 30 MB 级运行内存。

Compile 累计 Go 分配约 504 MB / 555 万次，Load 约 124 MB / 11.8 万次；这些也不是存活或峰值内存。
磁盘缓存把多数启动的编译阶段替换为读取与加载，当前约节省六倍该阶段时间；不会消除恢复表的成本。
同步写入只在缓存创建/失效重建发生，正常复用 DB 的 Scan 不写缓存。内嵌镜像省去文件查找/读取，仍须加载恢复。

独立阶段 CPU profile 显示：GetRequest HTTP/Dense 的预过滤调用约占 58%/67%，全零/稀疏输入约 99%/98%；
这些 C 调用包含实际 native 算法工作，不能全部说成跨界开销。编译解析约 22%、buildAlphabet 约 18%；
加载的 unpackImageBlob 约 30%、decodeImageBlob 约 26%，并有 GC 和 C 恢复成本。累计栈比例不能任意相加。
MITM 存在性更偏向 PCRE 确认（约 44%）；定位额外涉及 native 定位和 RE2 枚举，不能用存在性微场景代表。

T01 保存了 64 组完整结果对：实际 GetRequest/MITM、四种输入、两种模式，与独立完整 subject 参考比较，
并核对 Compile/Load 的早停顺序。性能轮次关闭诊断；路由普查、分阶段 profile 和 C 请求内存探针另行运行。
下一步按这些场景分别验证优化，不用未知生产权重制造“平均加速”。

## 测量条件

2026-10-18，Windows/amd64，i5-13490F，Go 1.22.12，clang、CGO_ENABLED=1、GOMAXPROCS=2。
基线与优化版分别编译为固定测试二进制，串行运行同一套输入与基准程序，报告三轮中位数。
`BenchmarkRuntimeScenarios` 包含四组规则、存在性/定位两种模式、四种输入，共 32 组；
每组比较完整命中 ID 和字节偏移的稳定指纹，全部一致。基准复用 Scratch 并预热确认器；
加载及首次扫描另行测量。MB 为十进制，B/op 是累计 Go 分配，不是 RSS，也不包含 C malloc。

GetRequest 是仓库的 4941 条实际指纹规则；HTTP912 是构造的 HTTP 响应，并非真实流量全集。

512 次重复 HTTP 头；Zero16K 为 16,384 个零字节。PCRE128 是专门放大共同前缀问题的合成规则，
其几十倍收益不能外推到所有 PCRE 规则或真实业务吞吐。

## 已实现的改进

### Unicode 字符类保留规则外层的过滤能力

旧 route-B 遇到 `[\w.-]`、`[^\d]`、POSIX 类等就放弃整条规则的预过滤，
即使规则还有很强的产品名、HTTP 头等必要字面量。现在将整个括号原子放宽为任意一个 rune，
保留括号外的结构。否定类也必须整体替换，不能把内部的 `\d` 局部替换后再取反。
改写后的语言是原语言的超集，真正的命中仍由 PCRE2 确认；超集出现假阳性不会直接上报。
括号扫描也处理 POSIX 内层括号、初始/转义的 `]`、`\Q…\E`，防止误认类或 lookaround 的结尾。

ASCII `s/k` 还可折叠为 Unicode `ſ/K`。提取器选择折叠后仍留在 ASCII 的必要片段，
按片段每个出现处计算完整折叠环的最大前后字节宽度，继续安全使用窗口和锚定。
`SK`、`sk-` 等没有足够长安全片段的短前缀展开有限 Unicode 变体，上限 64 个；
超过上限才退回完整验证，避免破坏 secret scanner 的零 always-on 约束。
ASCII 必要条件预检仍避开无法表达的 Unicode 折叠。
旧 v1/v2 镜像仍零编译加载；遇到这两个特殊字符时直接交完整 verifier，避免沿用旧触发器漏报。

GetRequest HTTP912 的诊断从每次 429 次 PCRE2 确认降至 3 次，处理的 subject 字节数
从 391,248 降至 2,736。剩余规则选择了共同的 HTTP 前缀，说明当前“最长字面量”
策略仍有选择性提升空间。这里没有声称所有 PCRE2 调用都能消除。

### 局部复核真正进入运行路径

有界 gate 原来会先进入 C 批量 NFA 分支，提前 `continue`，导致后面的局部 PCRE2 复核
无法生效。现在让这类 gate 使用已有的 head 上界，从首个必要字面量之前保留一个完整 rune 的
上下文起扫；后续真实命中仍在该后缀内。含 lookbehind 或无法证明界限的规则保留完整上下文。
测试覆盖首个触发失败而后面成功、文本/行锚、Unicode 词边界、反向引用、非法 UTF-8 和镜像往返。

### PCRE2 subject 在一次扫描内共享

旧确认接口为每条候选把同一 `[]byte` 转成 `string`。现在每个扫描线程/Scratch 持有独立的
不可变副本，第一条局部确认只复制请求的窗口；后续窗口超出缓存时按几何增长扩展。
每个扫描上下文的累计复制量从最坏 `O(K × L)` 降至摊还 `O(L)`，K 为候选数、L 为记录长度。
不使用 unsafe 借用输入内存，Scan 返回或提前停止时释放引用，异步 worker 也独立清理。
这只改善 subject 复制，不改变 PCRE2 自身的算法上界。
`O(L)` 指本层转换副本；依赖内部的 UTF-8 检查、非法 UTF-8 的归一化仍可能在每条确认中执行。

### 派生 NFA 表连续分配

单字 LimEx 的链边、异常边、follow/reach 标量表放入一个连续、无指针的数组；
多字版本先数异常行，再一次分配实际需要的异常边，链式位置不再先复制整行随后丢弃。
重建保留原始 follow，按位置生成的视图与原递推逐边比较，覆盖 64 位边界、稀疏/稠密和重复初始化。
派生表分配次数由随位置数增长降为每个 NFA 常数次；仍需读取原来的转移表。

### 密集字面量输出复用已扩大的容量

修复容量复用之前，密集 HTTP 的 CPU profile 中，约 70% 的总采样落在 C 字面量扫描调用，
约占热扫描自身的 83%。
检查发现 4,096 个字面量命中的记录，每次都会先以 2,240 对的初始估计扫描，发现不足后再完整扫一遍，
即使 Scratch 已经保留了 4,096 对的空间。现在 C 直接使用已有容量，只在真正超出空间时扩容重扫。
首次无匹配的大记录仍按原来的 8,192 对上限分配，不提前保留与正文长度成比例的缓冲。
此处消除一趟遍历，没有减少必须输出的字面量命中数；测试同时覆盖 Teddy 和 AC。

### 修复合并自动机的已有漏报

C 首字节过滤原来只使用 `firstUnanchored`。当 `[0-9]{6}` 与 `^(a)\1$` 混合时，
`aa` 没有数字，整个 merged 扫描被错误跳过。原基线二进制也可复现，Go 与 C 标量路径能命中。
现在首字节集合包含 anchored 与 unanchored 两类起点；覆盖单字/多字、combined、batch、
旧镜像加载与最终 PCRE2 确认，避免把预过滤假阳性当作结果。

和 NFA 候选持续活跃，密集场景仍然只有几 MB/s。纯字面量规则的稀疏/无匹配输入可达

首轮小样本里纯字面量与无触发 PCRE 的部分结果慢约 2–8%。反向顺序复测两个固定二进制，
每组 600 ms、三轮，8 组对照速度比为 1.002–1.020，均为零分配，未复现稳定回退。
不将这几个百分点当作性能提升。MITM 本身多数规则原已有效门控，本轮不是其普遍提速方案。

完整 MITM 真实语料为 1332 条、约 5.25 MB。最终存在性扫描中位数从 329.87 ms 降到
295.21 ms（约 1.12×），定位从 876.92 ms 到 866.92 ms，基本持平。
折叠片段使用完整的前后宽度，避免为了安全而让这些规则全部退回整记录扫描。

## 编译、加载与空间成本

先交错执行基线、优化二进制，修复折叠边界后再串行复测。下表基线为每轮 3 次、v4 为每轮 5 次，
均为三轮中位数，不将小幅的时间差当成确定收益：

| GetRequest 4941 条 | 基线 | 优化 |
| --- | ---: | ---: |
| Compile | 436.34 ms | 430.80 ms |
| LoadImage | 82.28 ms | 76.45 ms |
| LoadImage + 第一次 HTTP912 扫描 | 86.96 ms | 71.45 ms |
| Compile Go B/op | 498.63 MB | 503.85 MB |
| LoadImage Go B/op | 135.17 MB | 123.57 MB |
| LoadImage allocs/op | 701,378 | 117,752 |
| `.rehs` 最终大小 | 1,370,674 B | 1,454,568 B |

编译没有显著提速：本轮还增加了能参与门控的 NFA，约多 1% 的 Go 分配量，时间基本持平。
加载小对象分配减少约 83%，Go 分配字节减少约 8.6%，时间改善约 7%；独立时段的加载结果
仍有 GC/调频波动，不把本机中位数当成各平台保证。该数据下，镜像加载仍比重新编译快约 5.6 倍。

新版为增强门控保存更多自动机，比 v1 多约 84 KB，约 6%，即约 294 字节/规则。
新的稠密表示约 32 MB，结构精简后约 4.2 MB，最后压缩到 1.45 MB（约 1.39 MiB）。
文件仍比对应稠密表示小约 95.5%。新增空间确实换来了更好的执行计划，不能宣称这一轮所有尺寸都更小。
六条规则的内嵌示例为 880 字节；SHA256 为
`1069f24c86c4acee30ba7fd40ce286fecd05defca1f5a2f8cbc0a2e25c8172f4`。

格式升级到 v4，`LoadOrCompile` 发现旧版本后重建一次；`LoadImage` 继续零编译读取旧文件并原样导出，
因此显式保留旧镜像会继续使用旧预过滤计划。硬盘读写成本、原子替换和压缩开销的完整 v1 对照见
[编译镜像评估](COMPILE_IMAGES.md)。新版只多约 84 KB 文件传输量；按 100 MB/s 算新增约 0.84 ms，
这是带宽估计，不是机械硬盘实测，实际文件系统同步开销仍可能更大。

## 剩余瓶颈与下一步

设 P 为 NFA 位置数、W=ceil(P/64)、A 为压缩字母表大小、H 为字面量触发次数。
AC 字面量扫描为 `O(L + H)`；Teddy 还需要支付候选确认、哈希冲突和剩余字符串比较的成本，
不能对任意规则集承诺相同上界。本轮削掉了不必要的 `K × L` 复制，
局部复核只扫描各候选所需的后缀；后缀很长时仍可能接近整条记录。
没有把全部扫描变成与规则数无关的 `O(L)`。

1. **共同前缀和密集候选**：profile 先确认字面量过滤是密集样本的主瓶颈，上述复用去掉了多余遍历；
   其余候选确认和输出仍要支付。当前最长字面量策略忽略产品名等更稀有的因子。
   后续可在编译期按跨规则出现频率选择 trigger，或接入现有的必要因子 CNF，先检查第二个必要条件。
   代价是额外索引、状态及更大的编译计划，需要对密集正样本和窗口界限一起评估。
2. **always-on 与大位集**：稠密表示的 follow 最坏占 `O(P × W)`，reach 占 `O(A × W)`；
   merged NFA 合并遍历次数，但活跃位置多时仍需操作大量状态字和异常边。
   进一步可按选择性拆分 merged 组、跳过不活跃状态字，或让 C 运行表直接使用异常边紧凑布局。
   不能仅因磁盘字典压缩有效就推断压缩表在热扫描中更快。
3. **首次编译**：本轮 GetRequest 记录到 14,828 次前端 syntax.Parse、4,941 次 tryCompileNFA，
   共 620,239 个正向位置、2,173,359 个转移状态字和 760,804 个字母表状态字。
   解析树被字面量/窗口/自动机分析重复建立，且 repeat 展开及 Go/C blob 构造需要临时存储。
   下一步应在单次 Compile 生命周期共享不可变分析树和宽度结果，完成后释放，避免全局缓存留住规则。
   本轮没有声称消除了这些步骤，磁盘镜像仍是避免重复编译的主要手段。
4. **镜像加载**：字典展开、恢复 Go NFA、复制原生 blob 和 C malloc 仍占用启动时间及内存。
   本轮先消除大量小分配；进一步减少峰值内存需要更改运行表所有权或格式，
   例如只保留一个可直接消费的紧凑表。跨平台字节序、对齐、生命周期与边界检查需要继续保留。
5. **PCRE2 与定位结果量**：反向引用、递归、某些 lookaround 无通用线性时间保证；
   PCRE2 的匹配限制与失败行为仍由现有依赖控制。真正的高密度命中还必须支付输出数量的成本。
   不默认启用既有 anchorMerged/assertMerged 实验开关。

## 复现与验证

基线提交还没有新增的场景基准。复测时，在独立的临时 worktree 检出 `8911cf7d8`，
将本分支的 `runtime_performance_test.go` 复制到该 worktree 的同名目录，再分别 `go test -c`
生成两个固定二进制；不要在不同版本之间改动输入或同时运行性能基准。

```sh
CGO_ENABLED=1 go test -count=1 -timeout=5m ./common/minirehs/...
CGO_ENABLED=1 go test ./common/minirehs -run '^$' -bench '^BenchmarkRuntimeScenarios$' -benchmem -benchtime=350ms -count=3
CGO_ENABLED=1 MINIREHS_FULL_CORPUS=1 go test ./common/minirehs -run '^$' -bench '^BenchmarkMVSExistence/(MVS_Exist|MVS_Located)$' -benchmem -count=3
CGO_ENABLED=1 MINIREHS_DIAG=1 go test ./common/minirehs -run '^TestRuntime(GetRequestCandidates|CompileWork)$' -v
```

Windows PowerShell 用 `$env:CGO_ENABLED='1'` 等设置环境变量。基准应串行执行，
macOS/arm64 的 NEON、分配器、C 工具链和存储表现需原生复测。没有新增依赖或 CI 平台分支。
