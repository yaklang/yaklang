## 通过的有限合同

- 同连接拥有 CertificateRequest context 和请求序号；同 record 多请求保留不同序号，
  响应可按不同顺序到达。初始请求也计入观察序号，序号不是 PDU ID 或全局 PHA 轮次。
- 客户端 Certificate → CertificateVerify → Finished 逐步展示；空证书列表可拒绝请求，
  随后直接 Finished。应用密钥序号持续前进，PHA Finished 不重置为握手或新应用 epoch。
- 已观察的响应 context、重复/孤儿消息、响应中插入其他握手或应用数据有独立检查。
  缺失、未解释的前缀保留“不确定”，不把看不到的 Certificate 当作必然不存在。
- context/响应历史采用私有拥有值和 copy-on-write；集合、保留字节及关闭释放受预算约束。
  公开字段或握手明文字节的修改不改变后续关联。KeyUpdate 不清空连接历史。
- 新增四个 `tls.pha.*` 响应字段为 `origin=context`，不借物理或密文范围；晚到请求
  通过 `Certificate Request Admission → Earlier Response` 展示已有响应及请求序号，
  复用同一字段契约。已经发表的早期事件保持当时“请求未观察”的事实。

这些是当前 `tls` profile 的记录/消息观察合同，不是新的完整握手认证 profile。
AEAD 验证、观察到的 context/顺序、CertificateVerify 签名、Finished transcript MAC、
证书类型协商和 PKI 信任分开表达。产品不验证 CV 签名、Finished transcript MAC 或
PKI 信任；协商依赖的完整验收仍开放。

规则依据：[RFC 8446 §4.6.2](https://www.rfc-editor.org/rfc/rfc8446.html#section-4.6.2)。
未实现的 [RFC 8879 压缩证书](https://www.rfc-editor.org/rfc/rfc8879.html) 等消息仍保持
前缀不确定，不能据其后的 CV/Finished 反推缺少 Certificate。

## 从真实交换发现并修复的错误

最初 b126/ae87/d44 在普通完整来源上通过，但真实捕获顺序反例 829/830 证明：
服务端请求尚未送达解析器时，客户端合法响应被误报为未知 context，后续解析停止。
双方初始 Finished 已观察、TLS 尚未报告 gap，均不能证明对端当前前缀完整。

e7 保存每个原始 TCP 字节贡献者自己的 ACK，包括排队后才释放的乱序段；不用释放它的
另一个包或连接全局最新 ACK。只有记录贡献完整、对端 SYN/序号前缀已交付、无待解释
记录/握手字节或已知缺口时，才能将未匹配 context 当作确定错误。独立 session 和可靠
UDP 承载没有这份 TCP 证据，保持关联未知。序号回绕、半空间歧义和证据限额均有负控。

前缀未完整时，拥有并有界保留响应历史，继续解析；请求以后出现，再在该请求中关联。
请求永久缺失时没有请求序号，不捏造匹配。已观察到的响应 context 不能因随后丢包而遗忘。

两份实际 OpenSSL/Python 对端交换分别包含提供证书、空证书拒绝的两轮 PHA，均有 41 帧、
10 条真实 HTTP。来源 691 的独立 oracle 验证 23 个 AEAD tag、4 个 Finished MAC、
3 个 CV 签名；来源 777 验证 21 tag、4 MAC、1 签名。产品关联检查不冒称这些独立密码学验证。

832 从这两份交换派生八个捕获；保留全部捕获到的 IP/TCP/TLS 字节、序号、ACK 和密文，
只改变捕获顺序/时间或明确删去一个服务端请求包。不是八次新的对端交换。
