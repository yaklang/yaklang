# 企业流量分析需求分析与 AI 能力建设方案

> 状态：需求分析草案
> 基线日期：2026-10-20
> 适用范围：`common/pcapx/pcaputil`、`common/pcapx/pcapdb` 及现有 PCAP AI 工具
> 首期目标：面向授权调查人员的离线 PCAP/PCAPNG 流量调查与取证助手

## 1. 文档目的

本文从企业任务和调查流程出发，定义流量分析需要解决的问题、需要产出的事实、当前实现具备的能力，以及建设 AI 流量分析功能仍缺少的部分。

本文不是 `pcapdb` 的 API 教程。存储和查询用法见：

- `common/pcapx/pcapdb/README.md`
- `common/pcapx/pcaputil/BIN_PARSER.md`
- `common/pcapx/pcaputil/PROTOCOL_PARSER.md`

本文用于回答以下问题：

1. 企业流量分析通常包含哪些场景。
2. 每个场景需要完成什么动作、产出什么结果。
3. 哪些工作必须由确定性引擎完成，哪些可以交给 AI。
4. 当前 `pcaputil`、`pcapdb` 和 AI 工具已经覆盖到哪里。
5. 建设可用的 AI 流量分析功能还缺少什么。
6. 第一阶段应该做什么、做到什么程度、如何验收。

## 2. 核心结论

企业流量分析不是把整个 PCAP 直接交给模型阅读，而是一条事实提炼和调查链路：

```text
采集与保全
  -> 解码与重组
  -> 会话、事务和实体建模
  -> 汇总与基线
  -> 搜索与检测
  -> 关联取证
  -> Finding 与报告
  -> 处置与案件沉淀
```

当前实现已经具备一条以单次离线捕获为中心的底座：

```text
PCAP/PCAPNG
  -> pcaputil 协议识别、重组和字段解析
  -> pcapdb 原始包、协议消息、会话和方向流持久化
  -> Yak 工具有界查询和原始证据回溯
  -> AI Skill 编排基础查询
```

它最接近 DFIR 和离线取证产品，而不是完整的 NDR、NPM 或 DLP 平台。

建议将首期产品定位为：

> 面向企业安全、网络和取证分析人员的 AI 辅助离线流量调查助手。

产品价值不在于让 AI 声称“有没有攻击”，而在于：

- 用户可以用自然语言描述范围和问题。
- 系统用确定性查询完成统计、过滤和关联。
- AI 负责规划调查步骤、解释结果和组织报告。
- 每个结论都能回到捕获、消息、会话、流或原始包。

## 3. 产品边界

### 3.1 首期解决

- 导入、去重和校验 PCAP/PCAPNG。
- 查看捕获质量、协议、端点、会话和错误总览。
- 按时间、IP、端口、协议、字段和会话缩小范围。
- 重建请求响应和网络事务。
- 沿消息、会话、流和原始包关联取证。
- 对明确检测器产生的候选事件进行调查。
- 生成带证据引用、范围和限制说明的 Finding 与报告。
- 明确展示截断、缺口、加密、解析失败和未覆盖范围。

### 3.2 首期不承诺

- 不承诺仅凭单份 PCAP 建立长期“正常基线”。
- 不承诺自动发现所有攻击。
- 不把加密流量的元数据解释成已解密正文。
- 不把 IP 地址直接等同于资产、用户或责任人。
- 不在未经授权时解密、导出、删除或处置生产流量。
- 不把阻断、隔离等响应动作作为 AI 自动执行项。
- 不以本地 SQLite 子库直接替代企业级集中式、多租户流量存储。

### 3.3 后续可扩展

- 连续抓包和增量导入。
- 资产、身份、CMDB、DNS、证书和威胁情报关联。
- 跨捕获案件、长期基线和趋势分析。
- 企业级集中存储、分布式索引、权限和审计。
- 经授权的响应编排。

## 4. 用户与任务

| 用户 | 主要任务 | 最关心的问题 |
| --- | --- | --- |
| SOC 分析师 | 告警初筛、威胁验证、影响判断 | 是否真实、涉及谁、证据在哪里 |
| DFIR 分析师 | 时间线还原、证据固定、事件复盘 | 发生了什么、是否完整、能否复现 |
| 网络工程师 | 服务依赖、错误和容量分析 | 谁访问谁、是否失败、从哪里开始异常 |
| OT 安全工程师 | 工业协议和设备行为调查 | 哪台设备、什么命令、是否偏离过程 |
| 数据安全人员 | 敏感数据访问和外传调查 | 传了什么、去了哪里、是否获授权 |
| 工具开发者 | 扩展协议、检测器和报告 | 输入输出是否稳定、如何关联证据 |

典型任务可以描述为：

> 给定一个捕获、时间范围和调查假设，找到相关网络事实，形成可追溯的结论，并明确没有检查或无法确认的部分。

### 6.1 捕获初筛

需要回答：

- 捕获来自哪些接口，时间范围是什么。
- 包含多少包、多少字节、哪些协议。
- 哪些端点、会话和服务最活跃。
- 有多少截断包、解析错误、TCP 缺口和加密会话。
- 哪些分析能力没有启用，哪些数据无法判断。

成功标准：

- 所有统计由确定性聚合完成。
- 总览和明细使用同一范围和筛选条件。
- 总览明确标记部分覆盖、截断、采样和失败。

### 6.2 可疑主机调查

需要回答：

- 主机作为源和目的分别访问了谁。
- 使用了哪些协议、域名、服务、证书和端口。
- 是否存在周期连接、失败认证、异常上传或扫描行为。
- 哪些结论来自 DNS、TLS、HTTP、认证协议和会话的交叉证据。

注意：

- 企业 NAT、DHCP、代理和容器会使 IP 与真实资产或用户随时间变化。
- 只有流量时，IP 只能作为观测端点，不能直接认定为资产或人员。

### 6.3 应用事务重建

需要将一个业务请求还原成：

```text
Transaction
  -> Request Message
  -> Response Message
  -> Session
  -> Directional Stream
  -> Stream Chunks
  -> Physical Packets
```

需要保留：

- 发起方和响应方。
- 开始、结束和耗时。
- 协议、方法、路径、状态和错误。
- 请求响应关联依据。
- 字节截断、流缺口和解析失败。
- 每个结论对应的记录 ID。

### 6.4 加密流量研判

没有密钥时，至少要展示：

- TLS/QUIC 版本、SNI、ALPN、证书和端点。
- 握手成功、失败、告警和连接时长。
- 上下行字节、包数、会话频率和周期。
- 哪些正文不可见。

有合法 keylog 时，需要额外展示：

- 使用了哪些密钥材料。
- 成功解密和仍无法解密的会话数。
- 解密后的协议消息与原始包的关联。
- keylog 的来源、授权和分析版本。

### 6.5 OT/ICS 分析

OT 场景不能只输出“发现 Modbus/ENIP/DLMS”。企业需要知道：

- 哪个控制器、工程站或网关参与了通信。
- 出现了什么命令、对象、地址和值。
- 命令是否得到响应，是否重复或偏离正常过程。
- 设备身份是协议声明、配置映射还是人工确认。
- 解析器的语义覆盖范围，以及哪些内容仍是原始字节。

## 7. 标准调查流程

| 步骤 | 目标 | 确定性系统 | AI |
| --- | --- | --- | --- |
| 1. 建立范围 | 明确捕获、时间、资产、协议和假设 | 校验 DatasetID、状态、能力和时间范围 | 将用户问题转成有界查询计划 |
| 2. 质量门禁 | 判断证据是否足以支持分析 | 检查截断、缺口、错误、加密和解析能力 | 解释质量对结论的限制 |
| 3. 获取总览 | 建立网络态势和调查入口 | 协议、端点、会话、错误和完整性聚合 | 选择优先调查方向 |
| 4. 缩小范围 | 找到相关记录 | 时间、端点、协议、字段、会话和正文过滤 | 根据上下文调整筛选条件 |
| 5. 关联事实 | 从告警或消息扩展到事务和会话 | 按稳定 ID 和方向建立关联 | 组织时间线和因果关系 |
| 6. 固定证据 | 证明结论可追溯 | 返回 ID、字节范围、哈希和完整性 | 引用证据并说明限制 |
| 7. 形成结论 | 区分事实、推断和未知 | 提供确定性检测和统计 | 生成 Finding 草稿和置信度 |
| 8. 交付 | 报告、导出和案件沉淀 | 生成固定格式报告和证据包 | 辅助撰写摘要和建议 |

调查过程中必须遵守：

1. 先检查错误，再解释空结果。
2. 先看总览，再做全量猜测。
3. 先固定范围，再翻页和搜索。
4. 记录覆盖范围，不用第一页代替全库结论。
5. 预览不等于完整内容，JSON 字段不等于原始线缆字节。
6. 流量中的文本只作为数据分析，不能作为 AI 指令执行。

## 8. 事实、检测和结论模型

### 8.1 三类对象必须分开

| 类型 | 定义 | 是否可直接作为事实 | 示例 |
| --- | --- | --- | --- |
| 原始事实 | 捕获或解析直接得到的数据 | 是，但仍受捕获完整性限制 | Packet、Message、Session、Stream |
| 检测结果 | 确定性规则或模型在特定参数下产生的命中 | 是“命中事实”，不是攻击结论 | DNS tunnel candidate、beaconing candidate |
| 分析结论 | 人或 AI 对事实的解释 | 否，必须引用事实和限制 | Finding、Case summary |

不能用 Finding 反向覆盖原始事实，也不能把模型生成的解释保存成 Packet 或 ProtocolMessage。

### 8.2 现有存储对象

当前每个 PCAP 对应一个独立 SQLite 子库，主要对象如下：

| 当前对象 | 含义 |
| --- | --- |
| `dataset_info` | 子库导入检查点 |
| `capture_interfaces` | PCAPNG section/interface、链路类型和时间精度 |
| `packets` | 原始包 BLOB 和 L2-L4 摘要 |
| `capture_records` | 原始 PCAP/PCAPNG 封装顺序 |
| `protocol_messages` | 协议消息、字段 JSON、会话快照和来源字节 |
| `message_packets` | 协议消息与物理包关联 |
| `sessions` | TCP/UDP 双向网络会话 |
| `streams` | 会话的一个方向 |
| `stream_chunks` | 方向流的有界顺序字节块 |
| `session_packets` | 会话与物理包关联 |
| `stream_chunk_packets` | 流块与物理包关联 |

这组对象已经覆盖 Capture、Packet、Session、Stream 和大部分 ProtocolMessage。

### 8.3 建议补齐的分析对象

| 目标对象 | 作用 | 首期是否需要持久化 |
| --- | --- | --- |
| Transaction | 统一表达请求、响应、调用、状态和耗时 | 建议需要 |
| Entity | 资产、服务、域名、证书、用户、进程和设备 | 首期可先动态生成 |
| OverviewSnapshot | 固定一次聚合结果、范围和版本 | 建议需要 |
| Detection | 保存检测器、版本、参数、命中范围和证据 | P1 需要 |
| Finding | 保存结论、严重性、置信度、证据和限制 | P0 需要 |
| Case | 多个 Finding、证据和处置过程的集合 | P1 需要 |
| AnalysisRun | 解析器版本、配置、能力、时间和重建代际 | P0 需要 |
| AuditEvent | 导入、查询、导出、删除和授权记录 | P1 需要 |

### 8.4 稳定 ID 与关联

所有面向 AI 和用户的结果都应使用稳定 ID：

- `dataset_id`
- `packet_id`
- `message_id`
- `session_id`
- `stream_id`
- `chunk_id`
- `transaction_id`
- `detection_id`
- `finding_id`

不同 Dataset 和不同记录类型的数字 ID 不能混用。

## 9. 功能需求

优先级定义：

- P0：没有它，AI 调查闭环无法可靠成立。
- P1：企业日常场景需要，但可在基础闭环之后完成。
- P2：平台化、规模化或高级垂直场景。

| --- | --- | --- | --- |

## 10. AI MVP 工具契约

首期不建议继续让模型直接组合大量底层查询。应提供少量稳定、语义明确的工具。

### 10.1 工具集合

| 工具 | 作用 | AI 是否需要理解底层表 |
| --- | --- | --- |
| `pcap_import` 或升级后的 `load_pcapfile` | 导入、去重、查询进度和返回能力摘要 | 否 |
| `pcap_overview` | 返回确定性总览和质量信息 | 否 |
| `pcap_search` | 按时间和业务条件执行有界搜索 | 否 |
| `pcap_evidence` | 从记录 ID 获取消息、流、包和完整性线索 | 否 |
| `pcap_finding` | 保存结论、证据、范围和限制 | 否 |
| `pcap_report` | 生成 Markdown/JSON 报告和证据清单 | 否 |
| `manage_pcapdb` | 校验、列出、导出和删除库 | 少量 |
| `query_pcapdb` | 作为高级/兼容查询入口 | 是 |

### 10.2 统一查询信封

所有分析类工具应返回统一结构：

```json
{
  "dataset_id": "uuid",
  "operation": "search",
  "scope": {
    "time_range": ["start_ns", "end_ns"],
    "filters": {},
    "analysis_generation": "stable-id"
  },
  "items": [],
  "summary": {},
  "coverage": {
    "complete": false,
    "scanned": 0,
    "skipped": 0,
    "sampled": false,
    "truncated": false,
    "has_more": false,
    "next_cursor": 0,
    "limitations": []
  },
  "error": null
}
```

必须保证：

- `error` 优先于空 `items`。
- `complete=false` 不能解释成全量未命中。
- `sampled=true` 不能输出全库存在性结论。
- `truncated=true` 不能把预览当完整正文。
- `has_more=true` 必须保留可续查条件。

### 10.3 Finding 最小结构

```json
{
  "finding_id": "stable-id",
  "dataset_id": "uuid",
  "title": "short title",
  "claim": "what is asserted",
  "severity": "info|low|medium|high|critical",
  "confidence": 0.0,
  "status": "candidate|confirmed|rejected|inconclusive",
  "facts": [],
  "inferences": [],
  "unknowns": [],
  "evidence_refs": [
    {
      "record_type": "message",
      "record_id": 1
    }
  ],
  "scope": {},
  "limitations": [],
  "detection_refs": [],
  "created_by": "user|ai|detector",
  "analysis_generation": "stable-id"
}
```

Finding 不允许：

- 只写结论而没有证据引用。
- 把“未查完”写成“不存在”。
- 把截断消息当成完整请求或响应。
- 把候选检测命中直接写成已确认攻击。

### 10.4 AI 职责边界

| AI 可以做 | 确定性系统必须做 |
| --- | --- |
| 理解调查意图 | PCAP 解码、重组和字段解析 |
| 规划查询顺序 | 精确过滤、计数、Top-N 和时间聚合 |
| 选择范围和下一步 | 维护 ID 关联和一致性快照 |
| 解释事实之间的关联 | 执行检测器并保存参数和版本 |
| 生成 Finding 草稿 | 保存证据、哈希和完整性限制 |
| 建议导出或处置 | 执行授权、审批和真实动作 |

## 11. 当前实现基线

### 11.1 `pcaputil`

已具备：

- 实时抓包和 PCAP/PCAPNG 回放。
- TCP 重组、乱序、重传、缺口和多 worker。
- UDP 会话和空闲管理。
- 原生协议探测、消息定界和结构化字段。
- `ProtocolEvent` 拥有原始字节、字段和会话快照所有权。
- 捕获域、来源字节、解析状态、完整性和专家码。
- TLS keylog、UDP DecodeAs 和 CAN DecodeAs 等底层能力。
- 资源预算、取消和统计回调。

核心入口：

- `common/pcapx/pcaputil/capture_reader.go`
- `common/pcapx/pcaputil/reassembly.go`
- `common/pcapx/pcaputil/protocol_api.go`
- `common/pcapx/pcaputil/protocol_registry.go`
- `common/pcapx/pcaputil/bin_parser.go`

### 11.2 `pcapdb`

已具备：

- 每个捕获独立 SQLite 子库。
- 原始包 BLOB 和原始 PCAP/PCAPNG 封装。
- 协议消息、字段 JSON、会话 JSON 和消息原始字节。
- Session、方向 Stream、Stream Chunk 和物理包关联。
- 协议字段按需索引。
- 有界分页、结果字节预算、预览预算和稳定游标。
- 状态、能力、校验、重建、导出和删除。

尚未具备：

- 稳定 Transaction 查询模型。
- 确定性总览和聚合 API。
- 组合搜索和完整流正文搜索。
- Detection、Finding、Case 和 Report 持久化。
- 跨调用的固定分析代际。
- 完整导入配置和分析版本记录。

### 11.3 AI 工具

现有入口：

- `common/ai/aid/aireact/skills/pcap-analysis/SKILL.md`
- `load_pcapfile`
- `query_pcapdb`
- `manage_pcapdb`

现有模式可以完成小规模、明确问题的查询和证据回溯，但仍有以下问题：

- 旧 `analyze_pcap` 与新工具并存，入口和责任不统一。
- 模型必须使用底层 `query_type` 组合查询。
- 缺少确定性总览，模型可能尝试逐页统计。
- 缺少 Finding/Report，结构化结果无法沉淀。
- 评测主要覆盖小规模合成 HTTP/DNS 和库生命周期。

## 12. 差距与优先级

### 12.1 P0：形成可信的离线 AI 调查闭环

| 差距 | 当前情况 | 目标 |
| --- | --- | --- |
| 统一入口 | 新旧 PCAP 工具并存 | 默认使用导入 -> 总览 -> 搜索 -> 证据 -> Finding -> 报告 |
| 确定性总览 | 只有元数据和分页查询 | 协议、端点、会话、错误、截断、加密聚合 |
| 有界组合搜索 | 主要是等值、exists、missing | 时间、范围、子串、正则、OR、数组和 Session 条件 |
| 完整流搜索 | 预览截断后无法补回字节 | 安全扫描完整流并返回偏移和上下文 |
| Transaction | 只有消息级 `transaction_id/response_to` | 统一请求、响应、状态和耗时查询 |
| 证据模型 | ID 关联和单条导出 | 证据包、哈希、范围、版本和完整性 |
| Finding/Report | 仅 AI 自然语言输出 | 结构化 Finding、报告和证据清单 |
| 异步导入 | 同步阻塞 | 任务 ID、进度、取消、恢复和状态查询 |
| 导入配置 | `pcaputil` 支持但导入层未暴露 | keylog、DecodeAs、CAN/OT profile 和字段索引 |
| 分析版本 | 元数据信息不足 | 解析器、规则、配置、能力和重建代际 |
| 隐私安全 | 通用协议字段完整返回 | 运行时脱敏、提示注入隔离和敏感正文策略 |

### 12.2 P1：企业日常分析能力

- 资产、服务、域名、证书和身份候选实体。
- 确定性检测器：DNS 隧道、beaconing、扫描、认证失败、异常上传等。
- CMDB、IAM、DHCP、DNS 和威胁情报 enrichment。
- PCAP 专用 AI 分析循环。
- Case、跨 Finding 时间线和处置记录。
- 更完整的协议、加密、截断和 OT 评测集。

### 12.3 P2：平台化与规模化

- 连续抓包、流式检测和实时告警。
- 跨捕获长期基线和趋势。
- 集中式存储、分布式索引和查询调度。
- 多租户、RBAC、配额、保留期和访问审计。
- 经审批的响应动作编排。

## 13. 分阶段落地建议

### 阶段 0：统一入口和质量门禁

目标：确保 AI 不再混用新旧工具，并在错误或能力不足时停止分析。

交付：

- 明确 `load_pcapfile + query_pcapdb + manage_pcapdb` 为默认调查链路。
- 旧 `analyze_pcap` 降级为兼容入口或内部适配器。
- 统一 Dataset 状态、能力、完整性和分析代际字段。
- 统一空结果、失败、部分完成和未命中语义。

### 阶段 1：总览与有界搜索

目标：AI 可以稳定处理“这份捕获主要有什么”和“找出符合条件的事实”。

交付：

- `pcap_overview`。
- `pcap_search`。
- 时间、端点、协议、字段、范围和组合过滤。
- 完整流搜索和匹配偏移。
- 固定预算、续查和覆盖信息。

验收问题：

- 协议分布是什么。
- 某个 IP 双向访问了哪些端点。
- 哪些 HTTP 请求失败。
- 某个域名出现在哪些 DNS、TLS 和 HTTP 记录中。
- 哪些会话存在缺口或截断。

### 阶段 2：事务、证据和报告

目标：完成可交付的调查闭环。

交付：

- Transaction 视图。
- `pcap_evidence`。
- `pcap_finding`。
- `pcap_report`。
- Markdown/JSON 报告和证据包。

验收问题：

- 还原一次请求响应并给出耗时和状态。
- 某个异常候选有哪些跨协议证据。
- 哪些部分因为加密、截断或缺口无法确认。
- 导出一份可复核的报告和证据清单。

### 阶段 3：异步、配置和治理

目标：让较大的捕获和敏感数据可以安全、可控地分析。

交付：

- 异步导入任务和进度查询。
- 取消、恢复和失败重试。
- keylog、DecodeAs 和 OT profile 导入配置。
- 分析版本、配置指纹和重建代际。
- 运行时脱敏、权限、审计和导出策略。

### 阶段 4：企业增强

目标：从离线调查助手扩展到企业日常分析。

交付：

- 确定性检测器。
- 资产、身份、DNS 和证书 enrichment。
- PCAP 专用 AI 循环。
- Case 和跨捕获关联。
- 历史基线和企业集成。

## 14. 验收标准

### 14.1 正确性

- 同一捕获、筛选条件和分析版本产生可复现结果。
- 所有统计由确定性引擎完成，AI 不依据返回条数推算全量。
- 空结果必须同时满足 `err=nil`、`error=nil` 且覆盖完整。
- 失败、未完成、采样和未命中严格区分。
- 每个 Finding 至少引用一个事实 ID，或明确标记为纯假设。

### 14.2 证据完整性

- 每个证据引用包含 DatasetID、记录类型和记录 ID。
- 原始包、协议消息、流块和导出文件可独立核验。
- 截断、缺口、Midstream、加密和解析失败不能从结论中消失。
- 跨页和跨工具查询保留相同范围和筛选条件。
- 重建后旧分析代际的结果不能与新结果混用。

### 14.3 上下文与资源

- AI 不直接读取完整 PCAP 或完整流。
- 每次查询有条数、结果字节、预览、读取字节、时间和调用次数预算。
- 达到预算时返回部分完成和续查条件。
- 慢查询可取消，不阻塞其他 AI 任务。
- 导入大文件不阻塞推理循环，可查看进度和取消。

### 14.4 安全

- Cookie、Authorization、密码、PAN、PIN 等敏感字段按策略脱敏。
- PCAP 正文和字段中的指令不进入可执行的 AI 指令通道。
- keylog、解密正文、导出和删除均有明确授权和审计。
- 默认不覆盖已有导出文件，不接受无界路径和隐式删除。

### 14.5 数据集

首期评测不能只包含少量合成 HTTP/DNS，应至少覆盖：

- 正常 HTTP/DNS/TLS。
- 截断包、TCP 缺口、重传和乱序。
- 解析失败和未知协议。
- TLS 无 keylog 与有 keylog。
- UDP 会话和非标准端口。
- 至少一组 OT/CAN 工业协议。
- 分页、采样、续查、取消、重建和删除。
- 一份较大合成捕获，用于验证预算和内存边界。

## 15. 待产品确认的问题

以下问题会改变首期范围，需要在进入实现前确定：

1. 首期主要用户是 SOC、DFIR、网络运维还是 OT 团队。
2. 首期是否只支持离线文件，还是必须包含实时接口抓包。
3. 首期是否必须接入 CMDB、IAM、DNS 或威胁情报。
4. 是否允许使用 keylog，以及 keylog 和明文正文如何保存和销毁。
5. 首期是否允许导出原始敏感正文，还是只允许脱敏摘要。
6. 首期需要支持的最大 PCAP 大小、导入时间和查询时延目标。
7. 是否需要在首期提供 Detection，还是只做证据调查。
8. 是否需要跨用户共享 Dataset，以及 Dataset 的权限模型。

## 16. 建议的下一步

建议从两个依赖最少、收益最高的能力开始：

1. 统一 PCAP AI 工具入口和结果契约。
2. 实现确定性 `pcap_overview`。

完成这两项后，再实现 `pcap_search`、完整流搜索和 Finding/Report。检测器、专用 AI 循环和实时抓包应建立在稳定的总览、搜索和证据模型之上，而不是先于它们建设。

第一阶段最终应形成以下固定链路：

```text
导入或复用捕获
  -> 校验状态和能力
  -> 确定性总览
  -> 有界搜索
  -> 事务与流关联
  -> 原始包证据
  -> Finding
  -> Markdown/JSON 报告
```

只有这条链路可重复、可取消、可解释并且可追溯后，增加更多协议、检测器和自动化才有企业使用价值。
