# 企业流量分析实战场景手册

> 状态：场景与需求分析草案
> 基线日期：2026-10-20
> 关联设计：`docs/design/enterprise-traffic-analysis-requirements.md`
> 定位：说明企业拿到一份 PCAP/PCAPNG 后实际要做什么，以及这些工作对 AI 流量分析功能的要求

## 1. 先回答核心疑问

企业安全团队分析捕获流量，不只是做“溯源”，也不是单纯“提取 IOC”。

更准确地说，企业通常同时或按顺序完成以下任务：

1. **确认发生了什么**：是正常业务、配置错误、恶意活动，还是证据不足。
2. **确定影响范围**：哪些主机、用户、服务、域名、证书和业务事务涉及其中。
3. **还原事件链**：初始访问、下载、执行、外联、凭据访问、横向移动和数据外传分别发生在什么时间。
4. **提取可执行信息**：URL、域名、IP、文件、哈希、账号、主机名、证书、协议字段和业务对象。
5. **判断证据强度**：哪些是直接观察，哪些是推断，哪些由于加密、截断或缺口无法确认。
6. **支持处置**：封禁、隔离、重置凭据、排查其他主机、阻断业务风险。
7. **沉淀检测能力**：把调查结论转成规则、资产清单、基线和后续狩猎任务。
8. **形成可复核交付物**：事件报告、IOC 清单、证据包、时间线和案件记录。

可以用一句话概括：

> 从流量中建立“谁、在什么时间、与谁、做了什么、结果如何、证据在哪里、还有什么不知道”的可验证叙述。

### 1.1 常见工作不是一回事

| 工作 | 回答的问题 | 典型产物 | 主要依赖 |
| --- | --- | --- | --- |
| 流量初筛 | 这份捕获里有什么 | 协议、端点、会话和质量总览 | 聚合统计 |
| 信息提取 | 出现了哪些对象和指标 | IP、域名、URL、账号、主机名、证书、文件、哈希 | 协议解析和实体归一 |
| 告警研判 | 告警是否真实、严重程度如何 | Finding、证据、置信度、建议 | 告警上下文和关联 |
| 事件调查 | 一次安全事件如何发生、影响多大 | 时间线、影响范围、IOC、证据包 | 跨协议关联和原始证据 |
| 溯源 | 活动来自哪里、归因线索是什么 | 外部基础设施和历史关联 | 情报、历史数据和授权边界 |
| 威胁狩猎 | 没有现成告警时是否存在某类行为 | 检测假设、查询范围、候选事实 | 确定性检测器和基线 |
| 取证 | 能否证明结论、证据是否完整 | 原包、流、哈希、链和限制 | 原始字节、完整性和可复现性 |
| 业务分析 | 哪个服务慢、失败或依赖异常 | 服务依赖、错误率、延迟和事务 | RTT、重传、请求响应和时间序列 |
| 检测工程 | 如何让下次自动发现 | 检测规则、测试样本和误报边界 | 检测设计、数据集和版本化 |
| 处置支持 | 下一步应该做什么 | 封禁、隔离、凭据重置和排查清单 | 高置信事实和审批流程 |

其中“溯源归因”通常是最难、也最容易过度承诺的部分。仅有流量往往只能说明“与哪个基础设施通信”，不能直接证明“谁在网络另一端操作”。

## 2. 一份 PCAP 的标准分析顺序

### 2.1 先做捕获级总览

目标：在深入单个 IP 或协议前，建立样本边界。

至少要确认：

- 捕获来自哪里、何时开始和结束、持续多久。
- 使用了哪些接口、链路类型和抓包过滤条件。
- 包数、捕获字节和原始字节。
- 协议、传输、端口、内网/外网端点分布。
- 会话数量、最大会话和异常端口。
- 截断包、解析错误、TCP 缺口、重传和乱序。
- 加密会话、可解密会话和明文协议比例。
- 是否存在 DHCP、DNS、NBNS、Kerberos、LDAP、HTTP、TLS、SMB 等可用于识别主机和用户的信息。

这一步的产物不是“结论”，而是“调查范围和证据质量”。

### 2.2 建立资产与身份候选

PCAP 中通常没有权威资产库，需要从协议证据交叉推断：

| 信息 | 常见来源 | 可靠性 |
| --- | --- | --- |
| MAC 地址 | Ethernet、DHCP、ARP | 直接观察，但可能伪造或随机化 |
| IP 地址 | IP 头、DHCP、DNS | 直接观察，但 NAT/DHCP 会导致身份随时间变化 |
| 主机名 | DHCP Option 12、NBNS、mDNS、Kerberos | 协议声明，需交叉验证 |
| Windows 用户 | Kerberos CName、LDAP、NTLM | 需结合认证上下文 |
| 域名 | DNS、HTTP Host、TLS SNI | 直接观察，域名字符串不等于恶意 |
| 服务 | 端口、banner、ALPN、应用协议 | 端口只是提示，不能单独认定服务 |
| 进程/应用 | HTTP User-Agent、协议行为 | 可伪造，通常不能作为强身份 |
| 数字证书 | TLS 握手 | 可用于基础设施关联，不等于服务可信 |
| 文件 | HTTP/SMB/FTP/邮件对象 | 需校验长度、类型和哈希 |

### 2.3 按时间线串联网络事实

一个事件至少要按时间记录：

| 时间 | 事实 | 证据 |
| --- | --- | --- |
| 第一次 DNS 查询 | 主机查询了哪个域名 | DNS MessageID |
| TCP 建连 | 主机访问了哪个 IP 和端口 | SessionID、PacketID |
| 明文或解密请求 | 请求了什么 URL/方法/对象 | ProtocolMessageID |
| 文件传输 | 下载/上传了多少字节，是否完整 | StreamID、ChunkID、哈希 |
| TLS 握手 | 使用了哪张证书和哪个 ALPN/SNI | ProtocolMessageID |
| 后续外联 | 是否出现未知端口或持续回连 | SessionID、时间间隔 |
| 数据外传 | 哪个方向传输了多少字节，是否有敏感内容 | StreamID、匹配偏移 |

不要只输出一个 IOC 列表。IOC 没有时间、方向、主机和证据 ID 时，很难支持处置。

### 2.4 做跨协议关联

企业调查中最有价值的关联包括：

| 起点 | 关联方向 | 能回答的问题 |
| --- | --- | --- |
| DNS 查询 | DNS -> 响应 IP -> TCP/UDP Session | 域名实际连接到了哪里 |
| TCP Session | Session -> ProtocolMessage -> Packet | 连接里发生了什么 |
| HTTP 跳转 | 请求 -> 302/301 Location -> 新 Session | 下载链如何继续 |
| TLS SNI | ClientHello -> 证书 -> 目标 IP | HTTPS 访问了什么域名和服务 |
| Kerberos | 主机 IP -> 用户主体 -> 域控 | 哪台主机上哪个用户进行了认证 |
| DHCP | MAC -> 租约 IP -> Hostname | 某个 IP 在何时属于哪台主机 |
| File Object | HTTP/SMB/FTP -> 文件流 -> Hash | 下载/上传的具体文件是什么 |
| 告警 | Alert IP/域名 -> Session -> Stream -> Packet | 告警对应的原始证据在哪里 |

跨协议关联必须保留方向和来源，不能仅凭“时间接近”认定因果。

### 2.5 区分事实、推断和未知

建议每个结论都按以下格式输出：

```text
事实：10.7.10.47 在 22:39:49 UTC 查询 guiatelefonos.com 并解析到 92.118.151.9。
事实：10.7.10.47 随后与 92.118.151.9:443 建立 TLS 连接，SNI 为 guiatelefonos.com。
事实：该会话收到约 354 KB 应用数据，但正文因 TLS 加密不可见。
推断：该连接很可能对应公开分析所述的恶意载荷下载，但仅凭流量不能确认文件内容。
未知：没有 keylog，无法验证下载文件类型、哈希和内部代码。
```

这比直接写“该主机下载了 RedLine”更符合企业取证要求。

## 3. 案例一：疑似恶意软件感染（RedLine Stealer）

### 3.1 公开样本

- 来源：Unit 42 Wireshark Quiz
- 样本：`2023-07-Unit42-Wireshark-quiz.pcap.zip`
- PCAP：`2023-07-Unit42-Wireshark-quiz.pcap`
- 解压密码：`infected`
- 数据规模：2,497 个包，约 1.4 MB PCAP，捕获时间约 35.5 秒
- 公开答案页说明了感染主机、用户、时间和窃取信息类别

这是公开恶意流量训练样本，不应在真实企业环境中直接执行其中的恶意对象。

### 3.2 公开背景给出的问题

公开练习要求回答：

- 感染从什么时间开始。
- 受害 Windows 主机的 IP 和 MAC 地址。
- 受害主机的主机名。
- 受害主机上的 Windows 用户账号。
- 恶意软件尝试窃取什么类型的信息。

这类问题正好体现了企业调查的完整链路：识别对象、确认时间、还原行为、评估影响。

### 3.3 拿到 PCAP 后先做什么

第一步不是搜索“RedLine”。应按以下顺序：

1. 统计包、会话、协议和时间范围。
2. 找出内网网段和主要主机。
3. 标记 DHCP、DNS、NBNS、mDNS、Kerberos、LDAP 等身份线索。
4. 列出向公网发起的连接，尤其是 80、443 和非常用端口。
5. 对 DNS 查询、HTTP 请求和 TLS SNI 做时间顺序排列。
6. 对有下载行为的会话查看字节量、方向和完整性。
7. 再根据公开情报或告警确认恶意基础设施。

### 3.4 本样本中可以观察到的时间线

以下事实来自对此公开 PCAP 的实际查询。时间使用 PCAP 显示时间，公开答案使用 UTC；本手册不把两者混写。

| 时间 | 观察到的事实 | 企业含义 |
| --- | --- | --- |
| 06:39:22 | `10.7.10.47` 发起 DHCP 请求，随后 `10.7.10.9` 返回 DHCP 响应 | 可建立 IP、MAC 和租约线索 |
| 06:39:22 | `10.7.10.47` 发送 mDNS 查询 `DESKTOP-9PEA63H.local` | 可作为主机名候选 |
| 06:39:23 | 主机向 `10.7.10.9:53` 查询 AD/Kerberos/LDAP 服务记录 | 识别到域环境，域控为 `10.7.10.9` |
| 06:39:23 起 | 主机与域控的 88、389、445、135 等端口发生认证和 RPC/SMB 通信 | 可作为用户和主机身份关联来源 |
| 06:39:47 | 主机向 `623start.site` 发起 HTTP 请求 `GET /?status=start&av=Windows%20Defender` | 可疑的首次外联和宿主环境上报 |
| 06:39:48 | 主机再次请求 `623start.site` 的 `GET /?status=install` | 具有安装阶段/状态回传语义 |
| 06:39:49 | 主机请求 `92.118.151.9:80` 的 `GET /data/czx.jpg` | 伪装成图片的文件下载入口 |
| 06:39:49 | 服务器返回 `301 Moved Permanently`，`Location: https://guiatelefonos.com:443/data/czx.jpg` | 明文 HTTP 跳转到 HTTPS 下载 |
| 06:39:49 | 主机查询 `guiatelefonos.com`，随后建立 TLS 连接，SNI 为 `guiatelefonos.com` | 可把 DNS、SNI 和 TCP 会话关联 |
| 06:39:49 | 该 TLS 会话的服务器向主机发送约 354 KB 应用数据 | 提示可能发生了文件下载，但内容未解密 |
| 06:39:50 | 主机向 `194.26.135.119:12432` 发起 TCP 连接 | 非常用端口 C2 候选 |
| 06:39:50 到 06:39:58 | 双方在 `194.26.135.119:12432` 上交换约 550 KB TCP 载荷 | 提示可能发生了双向通信和数据外传 |

公开答案补充确认：

- 受害主机 IP 为 `10.7.10.47`。
- 主机名为 `DESKTOP-9PEA63H`。
- 用户账号为 `rwalters`。
- 恶意活动与 RedLine Stealer 相关。
- 窃取目标包括桌面和 Documents 文件、浏览器数据、加密货币钱包数据、应用 API key 和登录凭据。

### 3.5 现有工具实际能看到什么

使用 `pcap-inspect` 对样本重放后，可以观察到：

- DHCP 消息可解析。
- mDNS 查询可解析出 `DESKTOP-9PEA63H.local`。
- DNS 查询和响应可解析。
- HTTP 请求可解析出 Method、Path 和 Host。
- HTTP 301 响应可解析出 Location。
- TLS ClientHello 可解析出 SNI。
- Kerberos 消息可部分解析出复杂字段树。
- 非常用端口 C2 会话可识别为“unrecognized TCP”，并保留原始消息。

但当前工具还不会直接输出：

- `victim.hostname = DESKTOP-9PEA63H`
- `victim.user = rwalters`
- `url = http://623start.site/?status=install`
- `download.chain = HTTP 301 -> TLS SNI -> 354 KB response`
- `c2.candidate = 194.26.135.119:12432`
- `data_exfil.bytes ≈ 550 KB`

这正是 AI 分析层需要补齐的地方。

### 3.6 企业此时应当做什么

#### 确认与隔离

- 用 DHCP、NBNS、Kerberos 和资产库确认 `10.7.10.47` 当前对应的主机和用户。
- 隔离主机，但先保全内存、进程、启动项、浏览器数据和相关日志。
- 确认 `rwalters` 是否在其它主机登录，是否存在凭据复用。

#### 阻断与扩展排查

- 阻断 `623start.site`、`guiatelefonos.com`、相关 IP 和 `194.26.135.119:12432`。
- 搜索全网是否访问过相同域名、URL、SNI、IP 和文件哈希。
- 搜索是否存在相同 User-Agent、相同 HTTP 路径和 12432 端口连接。
- 检查代理、DNS、防火墙和 EDR 是否记录了同一活动。

#### 凭据和数据影响

- 将浏览器保存的密码、Cookie、会话令牌视为可能泄露。
- 重置该用户的重要账号，撤销活跃会话和 OAuth token。
- 检查加密货币钱包、API key、桌面和 Documents 文件。
- 检查同一时段是否有邮箱、VPN、SSO、云平台的异常登录。

#### 检测工程

- 对 `status=start`、`status=install` 这类安装状态回传建立 URL/行为规则。
- 对“HTTP 图片路径跳转到 HTTPS 后返回大文件”建立下载链规则。
- 对非常用端口、双向大流量和固定回连周期建立候选检测。
- 用本样本做成回归测试，验证 DNS、HTTP、TLS、TCP 和实体提取。

#### 报告

报告至少包含：

- 受害主机、用户、时间和网段。
- 初始外联、下载链、C2 和疑似外传时间线。
- 涉及的 URL、域名、IP、端口、SNI、User-Agent。
- 每个结论对应的 MessageID、SessionID、StreamID 或 PacketID。
- TLS 正文不可见、文件未提取、无法直接证明数据内容等限制。
- 已采取的隔离、封禁、凭据重置和扩展搜索动作。

### 3.7 这个案例对产品的直接要求

必须新增：

- 资产/身份候选提取：DHCP、mDNS、NBNS、Kerberos、LDAP、ARP。
- HTTP 事务链：请求、响应、Location、下载对象和响应大小。
- DNS/SNI/Session 关联。
- TLS 可见元数据、加密状态和 keylog 覆盖率。
- 非常用端口 C2 候选。
- Session 双向字节、持续时间和固定周期。
- 文件对象提取、类型识别和 SHA256。
- Finding 中同时保存事实、推断和未知。

## 4. 案例二：只有告警，没有完整事件结论（Big Fish in a Little Pond）

### 4.1 公开样本

- 来源：Malware-Traffic-Analysis.net 2024-09-04
- 场景：企业网络中发现主机感染告警，拿到 PCAP 和告警文件
- 网段：`172.17.0.0/24`
- 域：`bepositive.com`
- 域控：`172.17.0.17 - WIN-CTL9XBQ9Y19`
- 网关和广播地址：`172.17.0.1`、`172.17.0.255`
- PCAP 大小：约 1.7 MB

公开任务要求输出执行摘要、受害主机详情和 IOC。

### 4.2 企业处理步骤

#### 第一步：读取告警

需要把告警转换成结构化调查条件：

- 告警时间范围和时区。
- 源/目的 IP、端口、域名、URL 和文件哈希。
- 触发了哪条规则、规则版本和检测方向。
- 告警是来自 IDS、代理、DNS、防火墙还是 EDR。

#### 第二步：定位告警对应流量

- 按 IP/端口/域名查询 Session。
- 按时间窗口查询 ProtocolMessage。
- 沿 Message -> Packet 找原始包。
- 沿 Session -> Stream -> Chunk 找完整字节。

#### 第三步：从告警扩展到主机

- 用 DHCP 找租约、MAC 和主机名。
- 用 NBNS/mDNS 交叉验证主机名。
- 用 Kerberos/LDAP 找用户。
- 用 DNS 和 HTTP 找访问链。

#### 第四步：判断告警与活动的因果关系

需要区分：

- 告警规则命中了恶意行为。
- 告警命中了正常软件与恶意软件共享的通用特征。
- 告警命中了扫描、重传、测试或安全产品误报。
- 流量存在，但捕获缺少关键阶段。

#### 第五步：扩展搜索

- 相同域名/IP/URL 是否被其它主机访问。
- 相同文件哈希是否在其它 SMB/HTTP 会话出现。
- 是否有其它主机向相同端口或基础设施发起连接。
- 是否有横向认证、SMB 写入或远程服务调用。

#### 第六步：生成报告

输出应包含：

- 执行摘要。
- 受害主机详情。
- IOC/IP/域名/URL/哈希。
- 告警与流量的对应关系。
- 证据引用。
- 未覆盖和无法确认的部分。

### 4.3 为什么 AI 不能直接下结论

AI 容易犯的错误：

- 看到告警规则名字就认定恶意软件。
- 看到外网 IP 就认定 C2。
- 看到 HTTP 200 就认定下载成功。
- 看到大流量就认定数据外传。
- 把“未发现”说成“不存在”。

正确原则：

- 告警是检测结果，不是根因。
- 域名、IP、SNI 和 URL 是观察事实，不是恶意结论。
- 下载是否完整、文件是否可提取、哈希是否匹配，必须单独验证。
- C2 需要协议、时间、方向和跨会话证据支持。

## 5. 案例三：主机和用户识别

### 5.1 公开样本

Unit 42 的 “Identifying Hosts and Users” 教程提供了五份小 PCAP：

- 一份通过 DHCP 关联 MAC、IP 和主机名。
- 一份通过 NBNS 识别 Windows 主机名。
- 一份通过 HTTP User-Agent 推断平台和浏览器。
- 两份通过浏览器 User-Agent 识别 Android 和 iOS 设备。

该教程还说明：

- DHCP Option 50/12 可提供请求地址和主机名。
- NBNS 可提供 Windows/macOS 主机名。
- Kerberos CNameString 可提供 Windows 用户账号。
- LDAP 属性可提供用户姓名和目录信息。
- MAC、User-Agent 和主机名都可能被伪造或随机化，不能单独作为强身份。

### 5.2 实际观察结果

对 DHCP 样本重放后，当前解析器能输出：

```json
{
  "Hostname": "amVyZW1pYWhzLU1CUA==",
  "Requested IP": "172.16.1.38",
  "Observation": "unverified-lease"
}
```

这里的 `amVyZW1pYWhzLU1CUA==` 不是可直接展示的主机名，而是 base64 编码的 `jeremiahs-MBP` 一类值。对 AI 来说，直接返回这个字段会导致错误理解。

在 RedLine 样本的 Kerberos 消息中可以解出复杂的 DER/票据结构，但当前普通消息摘要没有稳定的 `user_principal` 字段。即使原始字节中包含用户信息，AI 也无法可靠地直接搜索。

### 5.3 企业实际需要的实体提取

| 实体 | 字段示例 | 必须保留的信息 |
| --- | --- | --- |
| Host | `ip`, `mac`, `hostname`, `domain`, `first_seen`, `last_seen` | 来源协议、Confidence、租约时间 |
| User | `account`, `realm`, `display_name` | 来源为 Kerberos/LDAP/NTLM、关联主机和时间 |
| Asset | `criticality`, `owner`, `environment` | 来自 CMDB 还是流量推断 |
| Domain | `fqdn`, `resolved_ips`, `first_seen`, `last_seen` | DNS 响应、SNI、Host 和证书 |
| Service | `ip`, `port`, `protocol`, `banner`, `ALPN` | 端口只是候选，协议探测才是证据 |
| Certificate | `subject`, `issuer`, `serial`, `sans`, `validity` | 来源握手和端点 |
| File | `name`, `url/session`, `size`, `mime`, `sha256` | 完整性、方向、来源和导出位置 |

实体提取不能只保存一个字符串。否则同名主机、NAT 后 IP 复用、重名用户和伪造 User-Agent 都会导致错误关联。

### 5.4 产品要求

- 从 DHCP 提取并解码 Hostname、Requested IP、Client ID、租约和服务器。
- 从 NBNS/mDNS 提取主机名和地址。
- 从 Kerberos/LDAP 提取用户名、域和票据关联。
- 从 DNS/SNI/Host/证书建立 Domain 和 Service 候选。
- 对每个实体保存来源消息 ID、时间、方向和置信度。
- 不把实体候选直接写入权威 CMDB；应先作为候选事实供人工或资产系统确认。

## 6. 案例四：恶意文件下载和对象导出

### 6.1 公开样本与任务

Unit 42 的 “Exporting Objects From a Pcap” 教程使用五份 PCAP，演示从以下协议导出对象：

- HTTP：导出文档、可执行文件和钓鱼网页。
- SMB：导出横向传播的恶意可执行文件。
- SMTP/IMF：导出垃圾邮件和恶意邮件。
- FTP：导出下载的 EXE 以及上传的窃密 HTML 文件。

教程明确要求：

- 用 `file` 验证文件类型。
- 用 SHA256 计算哈希。
- 检查 HTTP `Content-Type` 是否与真实文件类型一致。
- 检查导出对象的完成度，SMB 对象显示低于 100% 时可能是损坏副本。
- 在隔离环境中查看恶意 HTML，避免触发二次外联。

### 6.2 企业分析动作

1. 找到下载或上传的请求和响应。
2. 确认内容类型、声明长度和实际长度。
3. 沿 Stream/Chunk 重组完整对象。
4. 计算 SHA256，识别文件类型。
5. 检查会话是否截断、缺口或重组不完整。
6. 导出到隔离目录，禁止自动执行。
7. 用哈希和文件名搜索其它主机、代理和终端日志。
8. 把 URL、文件名、哈希和证据 ID 写入报告。

### 6.3 当前工具的主要缺口

目前 `pcapdb` 可以读取和导出协议消息、流块和原始包，但尚未提供统一的“协议对象”模型。

缺少：

- HTTP Object、SMB Object、SMTP Message、FTP Transfer。
- 对象名称、URL、方向、发起方、内容类型和声明长度。
- 完整性百分比和截断原因。
- 自动文件类型识别。
- SHA256 和可选的模糊哈希。
- 对象导出目录和审计记录。
- 对象与消息、会话、流块、原始包的双向关联。

AI 不应自己解析整个 TCP 流来猜一个文件，而应查询确定性的 Object API。

## 7. 案例五：加密流量与 keylog

### 7.1 公开样本与方法

Unit 42 的 HTTPS 解密教程使用 Dridex 感染的 PCAP 和 keylog。教程指出：

- 没有 keylog 时，只能看到 IP、端口和可能的域名（SNI），无法看到 URL、正文和对象。
- keylog 必须在捕获时同步获得；没有密钥通常无法事后解密。
- 有 keylog 后，可以恢复 HTTP 请求、DLL 下载和 POST C2。
- 教程给出的恶意示例包括 `foodsgoodforliver.com` 的 DLL 下载和 `105711.com` 的 POST。
- 教程还强调恶意网页和恶意载荷需要隔离处理。

### 7.2 企业的两种分析模式

#### 无 keylog

可以分析：

- 时间、源/目的 IP、端口、方向和字节数。
- DNS 查询和响应。
- TLS 版本、SNI、ALPN、证书和握手状态。
- 会话持续时间、上下行比例、连接频率和周期。
- 连接是否失败、是否有 TLS Alert、是否发生大文件下载。
- 与威胁情报、代理日志和端点日志的关联。

不能声称：

- 看过具体 URL、POST body 或下载文件内容。
- 仅凭 SNI 认定恶意。
- 仅凭流量大小认定数据外传。

#### 有合法 keylog

额外可以分析：

- HTTP 请求和响应。
- URL、Host、Method、状态码和头部。
- 解密后的文件对象和哈希。
- 请求响应关联和业务事务。
- POST 内容和敏感字段。

必须记录：

- keylog 来源、授权、访问者和时间。
- 解密成功/失败会话数。
- 不支持的密码套件和未解密流量。
- 明文和密钥的保存、导出和销毁策略。

### 7.3 现有能力与缺口

`pcaputil` 已有 `ParseTLSKeyLog` 和 `WithTLSSecrets`，可以支持部分 TLS/QUIC 解密。问题是 `pcapdb` 导入选项没有把 keylog 作为正式配置持久化，也没有统一的解密覆盖率输出。

需要补齐：

- 导入时接收 keylog，但不把原始 secret 写入普通查询结果。
- 记录“是否使用 keylog、成功解密多少会话、失败原因”。
- 把解密后的应用消息和原始 TLS Session 关联。
- 对密钥和明文设置更严格的访问、导出和审计策略。
- 对同一个 PCAP，区分“未加密”“已解密”“加密且不可见”。

## 8. 案例六：Windows/AD 横向移动

### 8.1 公开样本

`PCAP-ATTACK` 项目按 ATT&CK 阶段提供 PCAP，例如：

- Credential Access：Kerberoasting、密码喷洒、DCSync、LSASS/SAMR/RPC 访问。
- Discovery：SMB 共享枚举、RPC endpoint mapper、SAMR 用户/组枚举。
- Lateral Movement：SMBExec、PsExec、WMI、DCOM、RDP、ZeroLogon。
- Evasion：远程服务崩溃或异常行为。

这些样本的价值是展示“网络协议行为如何对应攻击阶段”。真实企业调查还应结合 EDR、Windows 事件日志和身份系统。

### 8.2 企业分析步骤

以横向移动为例：

1. 找到异常的 SMB、RPC、WMI、DCOM 或 RDP 连接。
2. 识别源主机、目的主机、用户和认证方式。
3. 判断认证是否成功，是否出现多次失败或密码喷洒。
4. 检查是否创建服务、写入可执行文件或远程执行命令。
5. 检查是否存在后续的服务启动、文件落地和回连。
6. 关联域控日志、EDR 进程树和 Windows 事件。
7. 输出受影响主机、账号、时间线和遏制建议。

### 8.3 企业目标不是“识别协议”

仅说“发现 SMB 流量”没有价值。企业需要：

- 谁从哪台主机访问了哪台服务器。
- 使用了哪个账号、认证是否成功。
- 读取或写入了哪些共享和文件。
- 是否创建了服务、计划任务或远程进程。
- 是否横向移动到更多主机。
- 攻击路径和受影响范围是什么。

因此，SMB/DCE-RPC/WMI/DRSUAPI 等协议需要事务级语义，而不只是消息摘要。

## 9. 案例七：DNS 隧道、C2 与 beaconing

### 9.1 公开样本

`PCAP-ATTACK` 的 Command and Control 目录包含：

- `cmds over dns txt queries and reponses.pcap`
- `C2_Foudre_Backdoor_DGA.pcapng`
- `rdp_tunneling_meterpreter_portfwd.pcapng`

这些样本可用于验证 DNS TXT、DGA、隧道和非常用端口 C2 候选检测。

### 9.2 DNS 隧道分析

需要观察：

- 查询类型是否异常，例如 TXT、NULL、非常用 TYPE。
- 子域名长度、标签数量、熵和随机性。
- 查询频率和固定周期。
- 查询与响应的大小比例。
- 是否反复访问同一权威域或不同随机域。
- 响应是否包含大块编码内容。
- 主机是否同时存在非常用 TCP/UDP 外联。

企业最终要回答：

- 哪台主机、哪个用户可能参与。
- 数据可能向哪个域名/服务器外传。
- 时间窗口和大致数据量。
- 是否能提取编码内容，是否因截断/加密无法确认。
- 其它主机是否出现相同域名、模式和周期。

### 9.3 Beaconing 分析

Beaconing 不是“有一条外网连接”。应分析：

- 目标基础设施重复出现。
- 连接时间间隔的集中度和波动。
- 每次上下行字节的稳定性。
- 会话持续时间、失败重试和抖动。
- 是否避开正常业务域名和端口。
- 与 DNS、TLS、HTTP 和认证事件的时间关系。

AI 可以用这些确定性统计解释候选，但不能仅凭“规律”证明 C2。

## 10. 案例八：数据外传与敏感信息

### 10.1 企业问题

- 是否有敏感数据离开内网。
- 数据从哪台主机、哪个用户、哪个进程或服务发出。
- 发送到哪个域名/IP/服务。
- 传输了多少，是否完整。
- 内容是凭据、个人信息、业务文件还是无法判断的加密数据。

### 10.2 分析动作

1. 找异常上行流量：目的新颖、时间异常、字节量异常、端口异常。
2. 找明文协议中的 HTTP POST、FTP STOR、SMTP、SMB 写入和其它上传行为。
3. 对正文进行敏感数据扫描：Authorization、Cookie、密码字段、PAN/PIN、API key、文件内容。
4. 对 TLS，先看 SNI、证书、会话字节和周期；只有合法 keylog 时才分析正文。
5. 关联下载链、C2 和后续外联，判断是否属于同一事件。
6. 生成脱敏证据，避免报告中再次泄露敏感内容。

### 10.3 产品要求

- 敏感字段识别和运行时脱敏。
- 上传对象和下载对象的方向模型。
- 文件、正文和凭据的访问审计。
- 外传字节、完整性和会话缺口。
- 置信度和“仅观察到加密流量”的限制。
- 不把敏感值完整送入 AI 上下文，默认只返回类型、位置和哈希/证据引用。

## 11. 非恶意场景：服务性能和业务故障

企业流量分析不只服务安全团队。网络和应用团队常问：

- 用户访问服务为什么慢。
- 哪个服务出现了大量连接失败。
- 哪个依赖导致请求超时。
- 重传、RTT、DNS 延迟还是应用错误。

### 11.1 分析动作

- 建立客户端到服务端的 Session 清单。
- 统计 SYN、SYN-ACK、RST、FIN、重传和缺口。
- 计算建连时间、首字节时间和请求响应时间。
- 解析 HTTP/DNS/数据库/MQTT 等协议状态和错误码。
- 按服务、端口、域名和客户端聚合错误率。
- 关联 DNS 延迟、TLS 握手和 TCP 层问题。

### 11.2 产物

- 服务依赖表。
- 失败会话和错误率 Top-N。
- 时间线和异常区间。
- 根因候选：DNS、TCP、TLS、应用或依赖服务。
- 证据会话和原始包。

这类场景同样是 AI 流量分析的重要需求，不能只按“恶意/非恶意”二分。

## 13. AI 应该怎样参与

### 13.1 适合 AI 的部分

- 把自然语言问题转成有界查询。
- 根据总览选择调查方向。
- 串联 DNS、HTTP、TLS、Session 和 Object。
- 把多个确定性结果组织成时间线。
- 识别事实和推断之间的差异。
- 生成 Finding 草稿、调查清单和报告。
- 推荐下一步查询或扩展搜索条件。

### 13.2 必须由确定性系统完成的部分

- 包解码、TCP 重组和协议解析。
- 时间过滤、字段过滤、计数和 Top-N。
- DNS 响应与连接的索引关联。
- 文件对象重组、长度校验和哈希计算。
- keylog 解密和覆盖率统计。
- 敏感字段扫描和脱敏。
- 证据 ID、完整性、哈希和版本。
- 检测器的可复现执行和参数保存。

### 13.3 一个合格回答的骨架

```text
调查范围：
  dataset、时间、网段、协议、筛选条件

已观察事实：
  主机/用户候选、域名、URL、会话、端口、字节数、状态

时间线：
  按时间排列的事实及证据 ID

行为链：
  初始访问/下载/执行线索/外联/横向/外传/业务异常

证据：
  MessageID、SessionID、StreamID、PacketID、文件 Hash

限制：
  加密、截断、缺口、未启用能力、采样和未检查范围

结论：
  Finding、严重性、置信度、影响和建议
```

## 14. 现有实现相对实战场景的缺口

### 14.1 已经有

- 原始包和原始捕获封装保存。
- TCP/UDP 会话和方向流。
- 多协议消息定界、字段解析和完整性状态。
- 消息、会话、流、流块和物理包关联。
- 有界分页、预览、游标和取消。
- 原始证据导出。

### 14.2 还缺

| 缺口 | 影响 |
| --- | --- |
| 没有确定性总览 API | AI 会尝试逐页统计，慢且不可复现 |
| 没有组合搜索和完整流搜索 | 无法稳定回答“同一主机在时间窗内的跨协议行为” |
| 没有统一 Transaction/Object/Entity | 只能看到消息和字节，难以得到业务事实 |
| 没有 Finding/Report | 结果无法沉淀和复核 |
| 没有导入配置和分析版本 | 无法复现 DecodeAs、keylog、协议 profile 的效果 |
| 没有异步导入 | 大捕获会阻塞 AI 调查 |
| 没有运行时脱敏 | 敏感值可能进入模型上下文和报告 |
| 没有专门的检测器 | AI 只能做通用浏览，难以稳定发现 C2、DNS 隧道等 |
| 没有实体关联和基线 | 无法可靠判断“某主机正常/异常” |
| 评测样本和答案结构有限 | 只测小规模 HTTP/DNS，不足以证明实战能力 |

## 15. 建议的实战 MVP

### 15.1 第一版工具

| 工具 | 说明 |
| --- | --- |
| `pcap_overview` | 返回捕获范围、协议、端点、会话、质量和加密总览 |
| `pcap_search` | 时间、端点、协议、字段、子串、范围和会话组合搜索 |
| `pcap_entities` | 返回主机、用户、域名、服务、证书和文件候选 |
| `pcap_transactions` | 返回协议事务和请求响应关联 |
| `pcap_objects` | 从 HTTP/SMB/SMTP/FTP 等提取对象和哈希 |
| `pcap_evidence` | 按记录 ID 返回原始包、流、对象和完整性 |
| `pcap_finding` | 保存事实、推断、未知、证据和置信度 |
| `pcap_report` | 生成 Markdown/JSON 报告和证据清单 |

### 15.2 第一批确定性检测

- DNS 高频/长标签/TXT/NULL/高熵候选。
- Beaconing 周期性和目标复用。
- 非常用端口长时间双向通信。
- 扫描和多目标连接失败。
- 密码喷洒和认证失败。
- SMB/RPC 横向移动候选。
- 明文凭据和敏感字段。
- 大文件下载和大流量上传候选。

### 15.3 第一阶段验收案例

必须至少通过：

1. RedLine 样本：识别受害 IP、主机名/用户候选、HTTP 安装回传、301 下载链、TLS SNI、未知端口 C2、双向字节和证据 ID。
2. DHCP/NBNS/Kerberos 样本：把 base64/复杂 DER 转换成可展示的主机名和用户候选，同时保留原始证据。
3. HTTP/SMB/SMTP/FTP 对象样本：导出对象、校验类型和哈希，报告完整性。
4. HTTPS + keylog 样本：无 keylog 时明确不可见；有 keylog 时恢复 URL、对象和 POST。
5. 横向移动样本：输出源、目的、账号、共享/服务和原始包证据。
6. DNS 隧道/C2 样本：输出检测候选、规律、时间窗口和限制。
7. 业务性能样本：输出失败率、RTT/重传、服务依赖和证据。

## 16. 关键约束

- 不能把公开样本的“答案”当成分析工具的能力。
- 不能把域名、SNI、IP 和告警命中直接认定为恶意。
- 不能把大流量直接认定为数据外传。
- 不能把 User-Agent、MAC、主机名直接认定为资产或用户。
- 不能把加密流量说成已解密。
- 不能在没有 keylog 时声称恢复 HTTPS 正文。
- 不能把协议字段中的指令当作 AI 指令执行。
- 不能报告“没有异常”而隐藏未检查范围和证据缺口。
- 不能在没有授权时导出、删除或处置敏感流量。
