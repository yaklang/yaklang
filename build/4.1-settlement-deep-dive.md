## 3. Proven second root cause

This was not a cancelled pipe and not a lost key.  It was a partial-batch
ordering cycle in `Cache.Barrier`:

```text
MarkPending: persistWG.Add(1)
  -> marshal pipe
  -> SnapshotForPersist (persisting=true)
  -> Save buffer contains a partial batch

old Barrier: resident.Wait() ---------------------------> needs FinishPersist
                                                        ^
                                                        |
old saver.Flush(), reached only after Wait -------------+
```

With a long saver timeout, the task had already crossed the marshal pipe but
had not reached the saver callback.  `FinishPersist` could occur only after a
saver flush; the old `Barrier` waited for that settlement before it issued the
flush.  The timer eventually broke the cycle, which explains the intermittent
whole-package "hang" without a pipe error or cancellation.

## 4. Deterministic RED → GREEN

Added `TestAsyncPersist_BarrierFlushesQueuedTasksBeforeWaiting` in
`common/utils/dbcache/async_persist_pipeline_test.go`.

The test uses a one-hour `SaveTimeout`, waits until the marshal worker has
queued exactly one saver task, then calls `Barrier`.  Thus the only permitted
way to settle is the barrier-driven flush:

- Restoring the old wait-before-flush ordering: deterministic RED at one
  second, `Barrier waited for persistWG before flushing the queued saver task`.
  Evidence: `build/4.1-barrier-order-red-20260813T013500.log`.
- Current implementation: GREEN immediately.  Evidence:
  `build/4.1-barrier-order-green-20260813T013600.log`.

The test also asserts that the save callback ran and the resident item was
evicted, so it checks settlement rather than only timeout avoidance.

## 5. Minimal production repair

`common/utils/dbcache/databasex.go` changes only `Cache.Barrier` ordering:

1. While `PendingCount() > 0`, synchronously call `saver.Flush()`.
2. Re-check pending work after each flush (with a one-millisecond yield while
   a marshal worker is still handing work to the saver).
3. Preserve the final `resident.Wait()` and async-drain boundary.

No data is discarded, no final barrier is skipped, and saver errors still
return immediately through the existing error path.  This breaks the ordering
cycle while retaining the established "no concurrent enqueue at final
Barrier" contract.
